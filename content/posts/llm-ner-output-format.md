PII 가드레일을 BERT (KoELECTRA + CRF) 와 sLLM (Solar / Bllossom / Qwen 의 LoRA SFT) 두 트랙으로 진행하면서, 처음에는 LLM 의 출력도 BERT 와 같은 형식으로 받으려 했다. 토큰 단위 BIO, 또는 토큰별 마스킹된 원문 복원. 둘 다 autoregressive 출력에는 비효율이라는 걸 깨달았다. 이 글은 그 과정과 새로 잡은 출력 형식의 설계를 정리한다.

## 처음 시도 — LLM 이 원문을 다시 generate

처음 학습 데이터는 이런 형태였다.

```
입력: 김철수 010-1234-5678 로 연락주세요
출력: <NAME>김철수</NAME> <PHONE>010-1234-5678</PHONE> 로 연락주세요
```

직관적이지만 두 가지 문제가 있다.

**1. autoregressive 가 원문을 다시 쓰는 비용**: 입력이 100 토큰이면 출력도 100 토큰을 그대로 다시 generate 해야 한다. PII 가 1 개 있건 0 개 있건. 7B 모델 기준 출력 1 토큰에 수십 ms. 1024 토큰 generate 면 그 자체로 10 초가 넘는다. BERT 가 한 번의 forward (수십 ms) 로 끝나는 것과 비교가 안 된다.

**2. 뒤로 갈수록 헛소리 위험**: autoregressive 의 본성상 출력 길이가 길수록 누적 오류가 커진다. 원문이 길면 뒤 토큰에서 무작위로 글자를 바꾸거나 빠뜨리는 경우가 생긴다. 우리가 마스킹하려던 게 아닌 부분에서 텍스트가 변형되면 가드레일이 깨진다.

## 두 번째 시도 — 어절 인덱스 + PII 단어만 출력

원문은 다시 안 쓰게 한다. 출력은 "어느 어절에 어떤 PII 가 있다" 만.

```
입력 (사전 처리로 어절 번호 매김):
  [0] 김철수 [1] 010-1234-5678 [2] 로 [3] 연락주세요

출력:
  [{"idx": 0, "label": "NAME", "text": "김철수"},
   {"idx": 1, "label": "PHONE", "text": "010-1234-5678"}]
```

원문 복원은 후처리 코드가 맡는다. LLM 은 "있다 / 없다 + 어디 + 무엇" 만 결정.

**장점**:

- 출력 토큰 수가 PII 개수에 비례. PII 없으면 `[]` 1 토큰. 짧다.
- 원문은 손대지 않으니 변형 위험 0.
- 평가도 깔끔해진다 — 어절 idx 와 label 만 비교.

**구현 과제**:

- 사전 코드 처리로 입력에 어절 번호를 매겨야 한다 (대괄호 + 정수).
- LLM 이 어절 인덱스를 정확히 출력해야 한다. 1024 토큰 안에서 인덱스 부정확하게 출력하면 PII 가 엉뚱한 자리에 매칭된다.

## 어절 인덱스 정확도 — 입력 설계의 효과

LLM 에게 인덱스를 정확히 맞히는 일은 쉽지 않다. 인덱스 자체가 단순 정수라 학습할 시그널이 약하다. 우리는 두 가지 보조 장치를 비교 중이다.

**A. 단순 어절 번호 입력**: `[0] 김 [1] 철수 [2] 010-1234-5678 …`. LLM 이 그대로 받아 사용. 짧고 단순.

**B. BERT 토크나이저로 분할한 sub-word 단위 입력**: BERT 가 만든 분할을 그대로 LLM 에게 넘긴다. NER 친화적 분할 이점.

A 가 단순하지만, 어절 정의가 모호한 한국어 (조사·어미 결합) 에서는 BERT 분할이 더 일관적일 수 있다. 다만 B 는 입력 토큰 수가 늘어서 1024 max token 을 빠르게 채운다. 7B 모델 기준으로는 종종 답을 끝까지 출력하지 못한다.

지금 결정은 **우선 A 로 시도해 평가셋 결과를 보고**, 인덱스 오류율이 크면 B 로 전환한다 — 정도다.

## 복합 ADDRESS 같이 이어진 라벨의 처리

ADDRESS 는 어절 여러 개에 걸쳐 나오는 경우가 많다. 예를 들면 이렇다.

```
[0] 서울에 [1] 있는 [2] 여의대로 [3] 파크원타워2 에서 …
```

출력 룰은 다음과 같이 정했다.

- `[0] 서울` 과 `[2] 여의대로 파크원타워2` 둘 다 ADDRESS.
- `[2]` 와 `[3]` 은 이어져 있으니 **`[2]` 만 출력하고** text 에 `[3]` 의 내용까지 합쳐서 적는다.
- `[3]` 을 따로 출력할 필요는 없다. 중복이고 후처리에서 동일한 결과로 풀린다.

```
[{"idx": 0, "label": "ADDRESS", "text": "서울"},
 {"idx": 2, "label": "ADDRESS", "text": "여의대로 파크원타워2"}]
```

이렇게 하면 출력이 또 한 번 짧아진다. 그리고 사용자 입장에서 보기에도 자연스럽다.

## 학습 데이터 형식 — 유해성 탐지 팀의 예시를 따라

같은 회사에서 유해성 분류를 맡은 분이 LLM SFT 를 이런 식으로 정리해뒀다. JSON 한 줄, messages 배열 안에 system / user / assistant 가 차례로 들어가는 chat 형식.

```json
{"messages": [
  {"role": "system", "content": "당신은 한국어 텍스트의 PII 를 탐지하는 분류기입니다. ..."},
  {"role": "user", "content": "[0] 김철수 [1] 010-1234-5678 [2] 로 [3] 연락주세요"},
  {"role": "assistant", "content": "[{\"idx\": 0, \"label\": \"NAME\", \"text\": \"김철수\"}, {\"idx\": 1, \"label\": \"PHONE\", \"text\": \"010-1234-5678\"}]"}
]}
```

PII 라벨 정의·룰을 system 에 풀어 적고, user 에는 어절 인덱스가 매겨진 원문, assistant 는 JSON 한 줄. reasoning 은 지금은 빼고, 분류 능력부터 본다.

## 정리

- LLM 에게 NER 의 모든 토큰을 generate 시키는 건 autoregressive 모델의 자연스러운 사용 방식이 아니다.
- 출력은 PII 가 있는 위치 (어절 인덱스) 와 라벨·텍스트만. 원문 복원은 후처리 코드.
- 어절 인덱스 정확도가 핵심 — 입력 단계에서 인덱스를 명시적으로 표시하고, 평가셋 결과로 부정확도를 측정한 뒤 입력 설계를 조정한다.
- 이어지는 ADDRESS 같이 어절 여러 개에 걸친 라벨은 첫 어절의 idx 에 통합 텍스트로 적어 중복을 피한다.

이 형식이 BERT 결과를 그대로 모사하려던 처음 방향보다 훨씬 LLM 의 강점을 살린다. 평가 결과가 나오면 다른 글에서 비교해 정리할 예정이다.
