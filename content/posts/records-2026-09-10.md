개인정보 탐지 모델(NER과 2차 LLM 검증으로 된 캐스케이드)과 멀티턴 공격 탐지 모델을 학습·평가·운영하면서 겪은 일을 분야별로 묶었다. 글마다 문제, 한 일, 결과, 키워드를 적었다.

## ML — 평가와 데이터

### [두 단계를 서로 다른 정답지로 채점하고 있었다](/posts/two-stages-two-answer-keys/)

- 문제: 1차 NER 뒤에 2차 LLM 검증을 붙이면 정밀도가 떨어지는 것으로 나왔다. 2차는 가린 것을 풀어 주기만 하는 단계라 그 방향은 나오기 어렵다.
- 한 일: 단계별로 다른 정답지로 채점하고 있었던 것을 찾았다. 같은 정답지로 다시 채점하고, 해제한 오탐과 잃은 정탐의 비율을 지표로 더했다. 같은 비교에서 정답지 결함(조직 금액을 개인정보로 둔 1,140자리)도 찾았다.
- 결과: 정밀도 0.9585 → 0.9631로 정정했다. 결함을 반영하면 해제 비율은 0.33:1 → 8.6:1이다.
- 키워드: 캐스케이드 평가, 정답지 일관성, F0.5, 골드셋 버전 관리

### [겉보기 개선은 평가셋의 틀을 외운 몫이었다](/posts/eval-set-leaked-without-sharing-a-sentence/)

- 문제: 평가셋 미탐을 보고 만든 학습 데이터로 점수가 크게 올랐다. 문장 중복 검사는 0건이었다.
- 한 일: 자리표시자 5-gram 틀 감사와 값 어휘 감사를 만들고, 오염 방향을 판정하는 기준을 정했다.
- 결과: 겉보기 F1 +0.020이 오염 축을 빼면 +0.003, 기관명 재현율은 오히려 하락이었다. 해당 버전은 승격하지 않고 오염 데이터를 격리했다.
- 키워드: 데이터 누출, n-gram 감사, 평가 위생

### [골드를 들여다본 순간, 다음 학습에 대해선 골드가 아니게 된다](/posts/looking-at-the-gold-spends-it/)

- 문제: 평가셋 미탐을 보고 보강하면 문장이 겹치지 않아도 평가셋이 오염된다. 임계값 보정에 쓴 정상 데이터 일부(약 14%)도 평가셋에 들어 있었다.
- 한 일: 갭 분석·생성·누출 검사·dev 셋 소모에 관한 규칙 네 개를 정하고, 겹친 항목을 뺀 데이터로 다시 쟀다.
- 결과: 오탐 감소 효과는 표본 밖에서도 유지됐다(약 35% → 약 34%). 검출 비용은 미검증으로 나눠 보고했다.
- 키워드: 평가 위생, dev 셋, 표본 밖 검증

### [문장이 하나도 겹치지 않아도 골드는 오염된다](/posts/gold-leaks-without-a-shared-sentence/)

- 문제: 유저 턴 해시 기준으로는 평가셋과 학습셋의 겹침이 거의 없었다.
- 한 일: 문자 5-gram 포함률 감사를 희소 행렬 곱으로 구현했다. 파싱 누락과 긴 문서의 사전 효과를 고치고, 이미 아는 누출을 100% 다시 잡는지로 도구를 검증했다.
- 결과: 학습셋의 약 7%가 평가셋과 틀을 공유했다. 제거 후 재감사 0건
- 키워드: 포함률, 희소 행렬, 감사 도구 검증

### [검색 인덱스도 모델이 본 데이터다](/posts/the-retrieval-index-was-seen-data/)

- 문제: 서빙 중에 조회하는 kNN 인덱스는 벡터만 있어 텍스트 누출 감사에서 빠져 있었다.
- 한 일: 서빙과 같은 인코더로 평가 대화를 임베딩해 코사인으로 대조했다. "모델이 본 것"의 목록(학습·보정·인덱스·프롬프트 예시)을 먼저 만드는 절차를 정했다.
- 결과: 평가셋의 영어 정상 구간 전체가 인덱스와 코사인 1.000이었다. 같은 공개 코퍼스가 출처였다.
- 키워드: 검색 기반 피처, 임베딩 감사, 데이터 계보

### [배포된 모델은 못 고치니 자를 고쳤다](/posts/fix-the-ruler-when-the-model-is-shipped/)

- 문제: 배포 중인 모델이 본 데이터와 평가셋 일부가 겹쳤다.
- 한 일: 평가셋을 수정하지 않고 버전업해 세 기준(정확 일치, n-gram 포함률, 인덱스 근접도)으로 겹친 항목을 뺐다. 언어·말투·형식·기법·도메인 칸별 공백을 세고, 칸의 용도에 따라 목표 건수를 정했다.
- 결과: 기존 평가 항목의 약 40%를 제외했다. 빌드를 다시 돌려 같은 결과가 나오는 것까지 확인했다.
- 키워드: 평가셋 버전 관리, 층화 평가, 라벨링 원칙

### [공격만 더 넣은 재학습은 오탐으로 돌아왔다](/posts/retraining-with-attacks-only-returned-false-positives/)

- 문제: 약한 공격 유형을 보강한 재학습 네 번이 매번 다른 형태의 정상 대화에서 오탐을 몇 배씩 늘렸다.
- 한 일: 공격에만 있는 겉모습(언어·형식·화법)을 모델이 배운다는 공통 원인을 찾고, 같은 겉모습의 정상 대조군과 짝 데이터 방향으로 정리했다. 오탐은 형식별 정상 셋으로 재도록 바꿨다.
- 결과: 단일 정상 셋에서는 보이지 않던 회귀(코드 대화 오탐 0% → 약 19%)를 형식별 측정으로 찾았다.
- 키워드: 대조 데이터, 지름길 학습, 형식별 평가

### [제품 성능은 '100건 중 몇 건'으로 말한다](/posts/speak-in-weighted-false-positive-rate/)

- 문제: F1과 PR-AUC로는 "정상 요청 100건 중 몇 건이 막히나"에 답할 수 없었다.
- 한 일: 칸별 표본을 늘리고, 트래픽 가중치와 형식별 출하 기준을 정하고, 재현율의 분모를 레이어 정의에 맞게 좁혔다.
- 결과: 같은 모델의 헤드라인 오탐률이 믹스 가정에 따라 두 배 넘게 움직인다는 것을 확인하고, 가중 오탐률과 칸별 통과 수로 보고하게 했다.
- 키워드: 제품 지표, 가중 오탐률, 출하 기준

### [정답에서 빠진 것과 정답에 잘못 들어간 것은 무게가 다르다](/posts/missing-and-wrong-labels-weigh-differently/)

- 문제: LLM으로 생성한 평가 문서의 정답에 누락과 과다 라벨이 섞여 있었다.
- 한 일: 채점 코드를 분석해 두 오류의 영향을 구분했다. 누락은 측정 범위를 줄이고, 과다 라벨은 가짜 미탐을 만든다. 표본을 직접 판정해 비율을 추정하고, 결합 판정 단계를 설계했다.
- 결과: 기관명 정답의 3분의 1가량이 과다 라벨임을 확인하고, 해당 라벨의 갭 분석을 보류했다.
- 키워드: 라벨 품질, 채점 규칙, 문맥 의존 라벨

## LLM

### [작은 모델에게 조건을 한 번에 주면 앞에서부터 놓친다](/posts/small-models-drop-instructions-from-the-front/)

- 문제: 4B 모델로 만든 평가 문서 중 쓸 수 있는 것이 29%였다.
- 한 일: 과제를 쪼개고, 허용 목록과 나쁜 예·좋은 예를 넣고, 뜻이 분명한 형식 실수만 복구했다. 단위 중복을 병합 단계에서 보정하고, 거부 샘플링으로 생기는 분포 쏠림을 측정했다.
- 결과: 통과율을 8% → 50% → 71%로 올렸다. 단위 중복 110곳을 스팬 어긋남 없이 보정했다.
- 키워드: 프롬프트 설계, 대조 예시, 거부 샘플링 편향

### [생성 모델이 턴을 덜 쓰면, 스키마로 강제한다](/posts/force-the-shape-with-a-schema/)

- 문제: 4B 모델이 요청한 턴 수의 60% 정도만 쓰고 문서를 짧게 써서, 8건 중 1건만 명세를 지켰다.
- 한 일: vLLM 구조화 출력으로 JSON 스키마를 강제했다(교환 배열 길이, 문서 필드 최소 길이, 첨부 위치 필드). 파서 버그와 서버 오류·공백 출력·토큰 한도를 처리했다.
- 결과: 첫 시도 통과율 78%, 재시도를 포함해 1,000건 중 963건(96%)을 동시 16으로 약 23분에 생성했다.
- 키워드: 구조화 출력, JSON 스키마, 합성 데이터

### [2차 LLM 검증을 끄기로 했다가 같은 날 되돌렸다](/posts/turned-off-the-llm-judge-then-back-on/)

- 문제: 한 방향만 담은 평가셋으로 2차 LLM 검증을 끄기로 결정했다.
- 한 일: 반대 방향 프로브로 결정을 되돌렸다. 판정 기본값을 "가림"으로 바꾸고, 번호형 사적 식별자는 규칙으로 처리했다. 값별 판정 근거를 반환하는 함수를 추가했다.
- 결과: 잘못 푼 이름 0건, 공인 질의 과차단 45건 중 1건, 정책 프로브 15/15
- 키워드: LLM-as-judge, 안전한 기본값, 규칙·LLM 하이브리드, 판정 근거 로깅

## MLOps

### [평가셋을 보지 않고 갭 분석용 dev 셋을 만들었다](/posts/dev-set-built-without-seeing-the-gold/)

- 문제: 갭 분석을 평가셋으로 하면 평가셋이 오염된다.
- 한 일: 자리표시자 기반 생성으로 정답을 구조적으로 보장하고 두 LLM을 섞었다. 보강 방향은 학습셋 통계로 정했다. ID별 시드·이어쓰기·병합 시 재검사·데이터 설명서를 만들고, 누출 감사를 양방향으로 했다.
- 결과: 문서 943건, 정답 스팬 12,533개. 희귀 라벨이 라벨당 2~16개에서 170~250개가 됐다.
- 키워드: 합성 데이터 파이프라인, 재현성, 데이터 카드, 누출 감사

### [임계값을 서빙이 아닌 사본 경로로 뽑고 있었다](/posts/threshold-calibrated-on-a-copy/)

- 문제: 임계값 산출 스크립트의 추론·후처리 사본이 서빙과 두 군데 달랐다(온도를 디코딩에 적용, 후처리 단계 누락).
- 한 일: 사본을 지우고 서빙 함수를 import했다. 같은 객체를 쓰는지를 테스트로 고정하고 다시 산출했다.
- 결과: 서빙과 스팬 단위 41/41 일치. 24개 값 중 1개가 경계를 넘어 규칙대로 갱신했다.
- 키워드: 학습·서빙 불일치, 보정, 온도 스케일링, CRF

### [재학습 대신 상수 두 개를 고쳤다](/posts/two-constants-instead-of-retraining/)

- 문제: 재학습이 연달아 실패하는 동안 오탐의 상당 부분이 게이트 임계값에서 나왔다. 보정 데이터에 문서·코드 형식이 없었다.
- 한 일: 형식별 정상과 공격으로 임계값을 격자 스윕하며 구제되는 공격과 새 오탐을 함께 셌다. 발동한 적 없는 죽은 조건을 찾았고, 상수 변경도 번들로 배포했다.
- 결과: CPU 전용 구성에서 가중 오탐률 약 35% 감소(LLM 재검 구성은 약 13%)
- 키워드: 임계값 보정, 교환비, 죽은 코드, 배포 번들

### [모델은 한 번만 올리고 나눠 쓴다 — vLLM 공유 서버](/posts/load-the-model-once-share-it-with-vllm/)

- 문제: 같은 4B 모델을 두 작업이 각자 올리려 했다. 고정 배치로는 500건에 4시간이 걸릴 참이었다.
- 한 일: vLLM 서버 하나에 모델을 올려 HTTP로 나눠 쓰게 했다. 서빙 가상환경을 분리하고, QAT 4비트 가중치와 메모리 비율을 정하고, 헬스 체크를 붙였다.
- 결과: 멀티턴 대화 1,000건을 약 23분에 생성했다.
- 키워드: vLLM, 연속 배치, PagedAttention, 서빙 환경 분리

### [공유 GPU를 이미 다른 vLLM 서버가 쓰고 있었다](/posts/sharing-a-vllm-server-on-a-shared-gpu/)

- 문제: 공유 GPU 16GB 중 13.8GB를 다른 작업의 vLLM 서버가 쓰고 있어 모델을 올릴 수 없었다.
- 한 일: 점유 원인을 추적하고, 허락을 받아 같은 모델의 서버를 OpenAI 호환 API로 공유했다. 부하를 보며 동시성을 조절하고, 생성 작업을 이어서 돌릴 수 있게 만들었다.
- 결과: 추가 GPU 메모리 없이 문서당 약 5초에서 약 1.6초로 줄었다.
- 키워드: GPU 공유 운영, vLLM, 동시성, 재개 가능한 작업

### [공유 GPU 서버에서 오래 도는 작업의 규칙](/posts/rules-for-long-jobs-on-a-shared-gpu/)

- 문제: 몇 시간짜리 작업이 세션 끊김, 무한 재시작, 남의 작업 침해에 노출돼 있었다.
- 한 일: setsid로 세션과 분리하고, 상태 파일로 재개하고, 감시자에 재시작 상한과 정지 기본값을 두고, 패치는 매칭 수를 단언하게 하는 등 규칙을 정리했다.
- 결과: 감시 경로가 출력 경로와 달라 정상 종료한 학습을 수십 번 재시작한 것 같은 과거 사고를 막는 운영 규칙과, 이번에 낸 작은 사고 두 건의 원인을 기록했다.
- 키워드: 장시간 작업, 감시자, 재개, 공유 자원

### [체크포인트는 어디에 있었나 — 포인터는 있는데 내용이 없었다](/posts/where-were-the-checkpoints/)

- 문제: 버전 비교용 체크포인트가 로컬 디스크에만 있었고, 배포 모델의 DVC 포인터는 원격에 내용이 없었다(push 누락).
- 한 일: 번들 사본과 크기·목록으로 동일성을 확인했다. 등록 완료 기준을 "원격 업로드와 내려받기 확인"으로 바꾸고, 보관할 에폭을 고르고, 폐기한 버전도 카드로 남겼다.
- 결과: 실행당 15GB 대신 버전당 선택 에폭만 보관해, 여섯 버전이 10GB를 넘지 않는다.
- 키워드: DVC, 모델 레지스트리, 체크포인트 계보

### [체크포인트만 바꾸면 배포가 아니다](/posts/a-checkpoint-alone-is-not-a-release/)

- 문제: 개선의 상당 부분이 규칙 코드에 있어서, 체크포인트만 교체하면 성능이 재현되지 않는다.
- 한 일: 배포 단위를 가중치·보정·임계값·규칙 코드·프롬프트의 묶음으로 정의했다. 버전 카드, 데이터 요약 로그, DVC 포인터, 매니페스트를 남기고, 산출물을 교체할 때 이전 판을 보존한다.
- 결과: DVC 포인터 17개로 관리하고, 두 배포본은 원격에 내용이 있는 것까지 파일 단위로 확인했다.
- 키워드: 모델 레지스트리, DVC, 재현성, 릴리스 단위

- 한 일: 단계마다 결과가 반드시 바뀌어야 하는 사례와 바뀌지 않아야 하는 경계 사례를 고정했다. 체인을 일부러 잘라 테스트가 실패하는지 확인했다.
- 결과: 일부러 넣은 고장에서 5건이 실패해 고장을 잡는 것을 확인했다.

### [규칙 하나가 조용히 꺼진 채로 숫자가 나오고 있었다](/posts/a-rule-was-silently-off/)

- 문제: import 실패를 받아내는 폴백 때문에 규칙이 꺼져도 측정이 에러 없이 끝났다. 앵커 없는 .gitignore 패턴 때문에 커밋된 적 없는 파일이 있었다.
- 한 일: 측정 헤더에 켜진 규칙과 경고를 출력하고, 경고가 실제로 발동하는지 확인했다.
- 결과: 수치마다 구성이 로그에 남는다. 새 클론 환경 테스트와 패턴 앵커 점검 항목을 정리했다.
- 키워드: 조용한 실패, 재현성, .gitignore, 설정 출처 기록
