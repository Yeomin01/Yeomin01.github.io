개인정보 탐지 모델(NER과 2차 LLM 검증으로 된 캐스케이드)과 멀티턴 공격 탐지 모델을 학습·평가·운영하면서 겪은 일을 분야별로 묶었다. 글마다 문제, 한 일, 결과, 키워드를 적었다.

## ML — 평가와 데이터

### [두 단계를 서로 다른 정답지로 채점하고 있었다](/posts/two-stages-two-answer-keys/)

- 문제: 1차 NER 뒤에 2차 LLM 검증을 붙이면 정밀도가 떨어지는 것으로 나왔다. 2차는 가린 것을 풀어 주기만 하는 단계라 그 방향은 나오기 어렵다.
- 한 일: 두 단계를 단계별로 다른 정답지로 채점하고 있었던 것을 찾았다. 같은 정답지로 다시 채점하고, 해제한 오탐과 잃은 정탐의 비율을 지표로 더했다. 같은 비교에서 정답지의 결함(조직 금액을 개인정보로 둔 1,140자리)도 찾았다.
- 결과: 정밀도 0.9585 → 0.9631로 정정했다. 정답지 결함을 반영하면 해제 비율은 0.33:1 → 8.6:1이다.
- 키워드: 캐스케이드 평가, 정답지 일관성, F0.5, 골드셋 버전 관리

### [문장은 하나도 겹치지 않았는데 평가셋이 새고 있었다](/posts/eval-set-leaked-without-sharing-a-sentence/)

- 문제: 평가셋 미탐을 보고 만든 학습 데이터로 점수가 크게 올랐다. 문장 중복 검사는 0건이었다.
- 한 일: 자리표시자 5-gram 틀 감사와 값 어휘 감사를 만들었다. 오염 방향을 판정하는 기준과, 갭 분석은 dev 셋으로만 하는 규칙을 정했다.
- 결과: 겉보기 F1 +0.020이 오염 축을 빼면 +0.003, 기관명 재현율은 오히려 하락이었다. 해당 버전은 승격하지 않고 오염 데이터를 격리했다.
- 키워드: 데이터 누출, n-gram 감사, 평가 위생, 골드셋

### [정답에서 빠진 것과 정답에 잘못 들어간 것은 무게가 다르다](/posts/missing-and-wrong-labels-weigh-differently/)

- 문제: LLM으로 생성한 평가 문서의 정답에 누락과 과다 라벨이 섞여 있었다.
- 한 일: 채점 코드를 분석해 두 오류의 영향을 구분했다. 누락은 측정 범위를 줄이고, 과다 라벨은 가짜 미탐을 만든다. 표본을 직접 판정해 비율을 추정하고, 결합 판정 단계를 설계했다.
- 결과: 기관명 정답의 3분의 1가량이 과다 라벨임을 확인하고, 해당 라벨의 갭 분석을 보류했다.
- 키워드: 라벨 품질, 채점 규칙, 합성 데이터, 문맥 의존 라벨

## LLM

### [작은 모델에게 조건을 한 번에 주면 앞에서부터 놓친다](/posts/small-models-drop-instructions-from-the-front/)

- 문제: 4B 모델로 만든 평가 문서 중 쓸 수 있는 것이 29%였다.
- 한 일: 과제를 쪼개고, 허용 목록과 나쁜 예·좋은 예를 넣고, 뜻이 분명한 형식 실수만 복구했다. 자리표시자 뒤 단위 중복은 병합 단계에서 보정했고, 거부 샘플링으로 생기는 분포 쏠림을 측정했다.
- 결과: 통과율을 8% → 50% → 71%로 올렸다. 단위 중복 110곳을 스팬 어긋남 없이 보정했다.
- 키워드: 프롬프트 설계, 대조 예시, 구조화 출력, 거부 샘플링 편향

### [2차 LLM 검증을 끄기로 했다가 같은 날 되돌렸다](/posts/turned-off-the-llm-judge-then-back-on/)

- 문제: 한 방향만 담은 평가셋으로 2차 LLM 검증을 끄기로 결정했다.
- 한 일: 반대 방향 프로브로 결정을 되돌렸다. 판정 기본값을 "가림"으로 바꾸고, 번호형 사적 식별자는 규칙으로 처리했다. 값별 판정 근거를 반환하는 함수를 추가했다.
- 결과: 잘못 푼 이름 0건, 공인 질의 과차단 45건 중 1건, 정책 프로브 15/15
- 키워드: LLM-as-judge, 안전한 기본값, 규칙·LLM 하이브리드, 판정 근거 로깅

## MLOps

### [평가셋을 보지 않고 갭 분석용 dev 셋을 만들었다](/posts/dev-set-built-without-seeing-the-gold/)

- 문제: 갭 분석을 평가셋으로 하면 평가셋이 오염된다.
- 한 일: 자리표시자 기반 생성으로 정답을 구조적으로 보장하고, 두 LLM을 섞었다. 보강 방향은 학습셋 통계로 정했다. ID별 시드·이어쓰기·병합 시 재검사·데이터 설명서를 만들고, 누출 감사를 양방향으로 했다.
- 결과: 문서 943건, 정답 스팬 12,533개. 희귀 라벨이 라벨당 2~16개에서 170~250개가 됐다.
- 키워드: 합성 데이터 파이프라인, 재현성, 데이터 카드, 누출 감사

### [임계값을 서빙이 아닌 사본 경로로 뽑고 있었다](/posts/threshold-calibrated-on-a-copy/)

- 문제: 임계값 산출 스크립트의 추론·후처리 사본이 서빙과 두 군데 달랐다(온도를 디코딩에 적용, 후처리 단계 누락).
- 한 일: 사본을 지우고 서빙 함수를 import했다. 같은 객체를 쓰는지를 테스트로 고정하고, 다시 산출했다.
- 결과: 서빙과 스팬 단위 41/41 일치. 24개 값 중 1개가 경계를 넘어 규칙대로 갱신했다.
- 키워드: 학습·서빙 불일치, 보정, 온도 스케일링, CRF

### [공유 GPU를 이미 다른 vLLM 서버가 쓰고 있었다](/posts/sharing-a-vllm-server-on-a-shared-gpu/)

- 문제: 공유 GPU 16GB 중 13.8GB를 다른 작업의 vLLM 서버가 쓰고 있어 모델을 올릴 수 없었다.
- 한 일: 점유 원인을 추적하고, 허락을 받아 같은 모델의 서버를 OpenAI 호환 API로 공유했다. 부하를 보며 동시성을 조절하고, 생성 작업을 이어서 돌릴 수 있게 만들었다. 프로세스 종료는 PID 기준으로 바꿨다.
- 결과: 추가 GPU 메모리 없이 문서당 약 5초에서 약 1.6초로 줄었다.
- 키워드: GPU 공유 운영, vLLM, 동시성, 재개 가능한 작업

### [체크포인트만 바꾸면 배포가 아니다](/posts/a-checkpoint-alone-is-not-a-release/)

- 문제: 개선의 상당 부분이 규칙 코드에 있어서, 체크포인트만 교체하면 성능이 재현되지 않는다.
- 한 일: 배포 단위를 가중치·보정·임계값·규칙 코드·프롬프트의 묶음으로 정의했다. 버전 카드, 데이터 요약 로그, DVC 포인터, 매니페스트를 남기고, 산출물을 교체할 때 이전 판을 보존한다.
- 결과: 배포 실행 폴더(169파일·8.1GB)를 포함해 DVC 포인터 17개로 관리한다.
- 키워드: 모델 레지스트리, DVC, 재현성, 릴리스 단위

## CI/CD

### [동등성 테스트는 양쪽이 같이 잘려도 통과한다](/posts/equality-tests-pass-when-both-sides-are-cut/)

- 문제: 패리티 테스트는 서빙·평가 체인이 같이 잘린 상태를 통과시킨다. 다른 환경에서 실제로 후처리 4단계가 빠진 고장이 났다.
- 한 일: 단계마다 결과가 반드시 바뀌어야 하는 사례와 바뀌지 않아야 하는 경계 사례를 고정했다. 체인을 일부러 잘라 테스트가 실패하는지 확인했다.
- 결과: 일부러 넣은 고장에서 5건이 실패해 고장을 잡는 것을 확인했다.
- 키워드: 회귀 테스트, 패리티 테스트, 고장 주입

### [규칙 하나가 조용히 꺼진 채로 숫자가 나오고 있었다](/posts/a-rule-was-silently-off/)

- 문제: import 실패를 받아내는 폴백 때문에 규칙이 꺼져도 측정이 에러 없이 끝났다. 앵커 없는 .gitignore 패턴 때문에 커밋된 적 없는 파일이 있었다.
- 한 일: 측정 헤더에 켜진 규칙과 경고를 출력하고, 경고가 실제로 발동하는지 확인했다.
- 결과: 수치마다 구성이 로그에 남는다. 새 클론 환경 테스트와 패턴 앵커 점검 항목을 정리했다.
- 키워드: 조용한 실패, 재현성, .gitignore, 설정 출처 기록

## 클라우드

### [데이터 생성용 LLM을 고를 때 모델보다 접근 권한이 먼저 막혔다](/posts/llm-backend-access-before-model-choice/)

- 문제: 후보 LLM 백엔드가 키 무효, 클라우드 모델 접근 미승인, 크레딧 부족으로 차례로 막혔다.
- 한 일: 접근 점검 순서를 정리하고, OpenAI 호환 인터페이스로 API·로컬 서빙을 갈아 끼우게 했다. 키는 환경 파일로만 관리했다.
- 결과: 같은 생성 코드로 API와 vLLM을 오갔고, 로컬 처리량은 직접 generate 대비 약 3배였다.
- 키워드: 관리형 LLM 서비스, 모델 접근 관리, 비밀정보 관리, 백엔드 추상화

### [쓰지도 않는 명단 1GB를 프로세스마다 올리고 있었다](/posts/a-list-loaded-for-nothing/)

- 문제: 폐지된 정책의 함수가 플래그를 보기 전에 376만 건 명단을 선로드했다.
- 한 일: 지연 로딩으로 바꾸고, 언제 올라가는지를 테스트로 고정했다.
- 결과: 프로세스 1,117MB → 39MB, 서빙 컨테이너 2,383MB → 1,662MB
- 키워드: 메모리 최적화, 컨테이너 리소스, 지연 로딩, 비용
