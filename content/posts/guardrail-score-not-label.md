## 가드의 출력이 뭐였나

멀티턴 공격 분류기의 추론 함수는 `(label, attack_prob)` 튜플을 반환했다. 세션을 받아 모델을 한 번 돌리고, softmax 확률에서 공격 클래스 값을 꺼낸 뒤, 임계값으로 라벨을 정해 둘을 함께 돌려주는 구조다.

겉보기엔 충분해 보인다. 라벨이 있으니 차단 여부를 알 수 있고, 확률이 있으니 신뢰도도 안다. 그런데 이 가드는 보안 레이어 스택의 한 칸이고, 실제 차단 결정은 그 앞단의 게이트웨이가 내린다. 게이트웨이는 여러 가드(PII·유해성·멀티턴)의 출력을 모아 정책을 적용하고, 운영 중에 임계값을 조정한다.

이 구조에서 위 출력은 두 가지를 숨기고 있었다.

## 숨겨진 것 1 — 감쇄된 확률

반환되는 `attack_prob` 은 모델의 raw 확률이 아니었다. 정상 기술 대화(코딩·DevOps·보안 방어)가 공격으로 오탐되는 걸 줄이려고, 도메인 감쇄 후처리가 들어가 있었다.

```python
attack_prob = softmax(logits)[ATTACK]
if domain_dampen:
    score = _coding_domain_score(dialogue)   # 코딩/방어 신호 강도
    attack_prob = attack_prob * (1 - score) ** 2
```

즉 출력 확률은 `모델 raw 확률 × 감쇄` 였다. 게이트웨이 입장에서 0.15 라는 값을 받으면, 이게 "모델이 원래 0.15 로 봤다"인지 "모델은 0.9 로 봤는데 코딩 도메인이라 0.15 로 깎았다"인지 구분할 방법이 없다. 두 경우는 의미가 완전히 다른데, 출력은 같다.

감쇄는 휴리스틱이다. 키워드 목록과 형태소 패턴으로 도메인을 추정하는 규칙이라, 틀릴 수 있다. 게이트웨이가 raw 확률을 봤다면 "모델은 공격이라 봤지만 가드가 감쇄했다"는 신호를 정책에 반영할 수 있다. 감쇄된 값만 받으면 그 판단의 여지가 사라진다.

## 숨겨진 것 2 — 임계값을 누가 갖는가

라벨은 `attack_prob ≥ threshold` 로 정해진다. 그러면 그 임계값을 가드가 고정해서 라벨까지 정해 보내는 게 맞을까, 아니면 점수만 보내고 게이트웨이가 정하게 두는 게 맞을까.

게이트웨이가 임계값을 조정해 운영한다면, 답은 후자다. 라벨만 보내면 게이트웨이는 동작점을 바꿀 수 없다. 위험등급을 낮음·중간·높음으로 나누는 것도, 여러 가드의 점수를 합산하는 것도, 연속 점수가 있어야 가능하다. 라벨은 그 모든 걸 0/1 로 뭉개버린다.

그리고 임계값 자체에 함정이 하나 있었다. 운영 임계값을 자동 보정하는 스크립트가 `thresholds.json` 에 값을 써두는데, 거기 적힌 모델 판정 임계값이 `1.0` 이었다. ROC 의 Youden's J 로 보정한 값인데, in-distribution 평가셋에서 모델이 거의 완벽(F1 0.99)하다 보니 최적 임계값이 극단으로 밀린 결과다. 임계값이 1.0 이면 모델 경로는 사실상 절대 안 터진다. 합성 데이터에 가까운 분포에서 보정한 임계값을 그대로 운영에 쓰면 이런 퇴화가 생긴다.

## 어떻게 바꿨나

추론 함수가 구조화된 결과를 반환하게 했다.

```python
{
  "raw_prob":   0.93,                  # 감쇄 전 순수 모델 확률
  "final_prob": 0.15,                  # 도메인 감쇄·에스컬레이션 보정 후
  "decision":   "BENIGN",              # final_prob ≥ threshold 기준 권고
  "threshold":  0.5,                   # 사용한 임계값(참고용)
  "reason":     ["domain_dampen(0.60)"]  # 적용된 보정
}
```

`raw_prob` 과 `final_prob` 을 나눠서, 게이트웨이가 모델의 원래 판단과 가드의 보정을 둘 다 볼 수 있게 했다. `reason` 은 어떤 보정이 왜 적용됐는지를 드러낸다 — 비어 있으면 raw 그대로라는 뜻이다. `decision` 은 어디까지나 가드의 권고이고, 게이트웨이는 이걸 무시하고 자기 임계값을 `raw_prob` 이나 `final_prob` 에 적용할 수 있다.

판정에 쓰는 임계값도 바꿨다. 퇴화한 `thresholds.json` 의 1.0 대신, 학습 종료 시 held-out 평가에서 F1 을 최대화하도록 보정한 `gate.json` 의 값(0.5)을 쓴다. 어차피 최종 판정은 게이트웨이 몫이라, 가드가 들고 있는 임계값은 권고용 기준일 뿐이다.

## 정리

탐지 모델을 게이트웨이 뒤에 두는 구조라면, 모델이 라벨을 확정해서 보내는 건 정보를 버리는 일이다. 게이트웨이가 임계값과 정책을 갖고, 여러 가드를 합쳐 결정하려면 연속 점수가 필요하다. 그리고 그 점수는 후처리로 덮어쓴 값이 아니라, 모델이 실제로 본 값과 보정한 값을 나눠서, 무엇을 왜 바꿨는지까지 같이 내보내야 한다. 차단은 가드가 아니라 게이트웨이가 결정한다.
