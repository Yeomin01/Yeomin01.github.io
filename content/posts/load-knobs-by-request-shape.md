## 이어서

앞의 여섯 글은 하나씩 따로 겪은 일이다. 디코딩 병목, 나눠 쓰는 GPU, 스레드 수, 잠금, GPU 메모리, 프로세스 수. 이번엔 그걸 한 표로 모은다. 다음에 같은 일을 하면 이 표부터 볼 생각이다.

## 손잡이와 부작용

| 손잡이 | 잘 듣는 경우 | 내가 잰 효과 | 부작용 |
|---|---|---|---|
| 요청 안의 문장을 묶어 한 번에 | 문장이 많은 요청 | 16문장 1.6~4.8배, 1문장 1.2배 | GPU 메모리 최대치가 커진다 |
| GPU 왕복 줄이기 | 모델을 GPU에 올린 경우 | 디코딩 271ms → 11ms | 결과가 같은지 따로 확인해야 한다 |
| GPU로 옮기기 | 긴 요청, 혼자 쓰는 GPU | 16문장 지연 284ms → 62ms | 나눠 쓰는 GPU에서 1문장은 두 배 느림. 남이 메모리를 채우면 실패 |
| 연산 스레드 수 줄이기 | 동시 요청이 많을 때 | 동시 16에서 226 → 357문장/초 | 혼자 온 큰 요청은 119ms → 284ms |
| 요청 단위 잠금 풀기 | 한 번에 하나만 돌던 레이어 | 동시 8에서 1.3 → 4.5건/초 | 스레드별 사본이 메모리와 첫 요청 지연을 먹는다 |
| 레이어 전용 프로세스 | 짧은 요청, 파이썬 구간이 천장일 때 | 상한 5.4 → 9~10건/초 | 메모리가 프로세스 수만큼. 운영 대상이 늘어난다 |
| 묶음 크기 줄이기 | GPU 메모리가 급할 때 | 7.4GB → 4.3GB | 처리량 절반 |
| 동시에 올리는 묶음 수 제한 | GPU 메모리가 급할 때 | 7.4GB → 2.4GB, 처리량 그대로 | 코드 변경이 필요하다 |

마지막 줄 하나가 빠져 있다. **여러 요청의 문장을 모아 한 묶음으로 보내는 것**이다. 한두 문장짜리 요청이 몰릴 때 가장 맞는 처방인데, 기다리는 창만큼 지연의 바닥이 올라가고 구현이 복잡하다. 이번에는 안 해 봤고, 재지 않은 것은 표에 넣지 않았다.

## 요청 모양으로 다시 읽으면

같은 표를 세로로 자르면 이렇게 된다.

- **한두 문장짜리 대화 요청이 대부분이면.** 묶음 효과가 작다. 요청마다 드는 파이썬 구간이 천장이다. 전용 프로세스가 듣고, GPU는 나눠 쓰는 한 손해다.
- **수십 문장짜리 응답·문서가 대부분이면.** 묶음이 가장 크게 듣는다. GPU로 옮길 만하고, 그때는 메모리 최대치를 같이 본다.
- **둘이 섞이면.** 큰 요청 하나가 작은 요청들을 세우지 않게 하는 게 먼저다. 요청 단위 잠금이 있으면 그것부터 본다.

트래픽이 어느 쪽인지 모르고 손잡이부터 돌리면 반은 헛돈다. 나는 요청 길이 분포를 끝까지 몰랐다. 그래서 조건을 나눠 답할 수밖에 없었다.

## 결론을 뒤집은 건 재는 방법이었다

이번에 결론이 뒤집혔거나 뒤집힐 뻔한 자리가 넷이다. 넷 다 손잡이가 아니라 측정 쪽이었다.

- **한 가지 요청 크기로만 쟀다.** 16문장으로 재고 GPU가 세 배 빠르다고 했다. 1문장에서는 반대였다.
- **운영에 없는 조건으로 쟀다.** 레이어 하나만 띄워 스레드 24로 쟀다. 서버에서는 4였다.
- **스레드를 데우지 않고 쟀다.** 스레드별 준비 시간이 측정 구간에 들어가 동시 처리가 느리게 나왔다.
- **로그의 처리 시간을 지연이라 읽을 뻔했다.** 잠금을 쥔 뒤부터 재는 시간이라 줄 서서 기다린 몫이 빠져 있다. 그 값으로 견주면 잠금이 있는 쪽이 빨라 보인다.

하나 더, 내 측정은 전부 닫힌 루프였다. 동시 N개가 응답을 받은 뒤에야 다음을 보낸다. 서버가 느려지면 보내는 쪽도 같이 느려져서 서버를 봐준다. 실제 트래픽은 서버 사정과 상관없이 온다. 그래서 내 숫자는 **배수로만 읽고**, 버틸 수 있는 도착률로는 읽지 않는다.

아래 그림에서 서버를 느리게 만들어 보면, 닫힌 루프는 보내는 속도가 같이 줄어 줄이 일정하게 남고, 열린 루프는 줄이 계속 길어진다.

## 넓게 보면

손잡이는 많지 않고, 대부분 알려져 있다. 어려운 건 어느 손잡이가 **지금 이 트래픽에** 듣는지 아는 것이고, 그건 재 봐야 안다. 그런데 재는 일이 손잡이를 돌리는 일보다 틀리기 쉽다. 손잡이를 잘못 돌리면 숫자가 나빠져서 티가 나지만, 잘못 재면 그럴듯한 숫자가 나온다.

그래서 순서를 정했다. 요청 길이 분포를 먼저 본다. 운영과 같은 프로세스 모양에서 잰다. 요청 크기를 둘 이상으로 잰다. 그다음에 손잡이를 고른다.

## 메모

- 손잡이를 고르기 전에 요청 길이 분포를 본다. 짧은 요청과 긴 요청은 처방이 반대다.
- 효과를 적을 때 부작용을 같은 줄에 적는다. 부작용 없는 손잡이는 이번에 하나도 없었다.
- 닫힌 루프로 잰 처리량은 배수로만 쓴다. 실제 도착률을 버티는지는 다른 시험이다.
