## 반만 맞는 설명들

Java Spring과 Python 웹 서버 구조를 비교한 자료를 읽다가 몇 가지 설명에서 걸렸다.

- Java는 멀티스레드로, Python은 GIL 때문에 멀티프로세스로 코어를 쓴다.
- 프로세스 하나는 코어 하나에서 돈다.
- Uvicorn은 프로세스당 스레드가 하나라서 요청이 꼼짝없이 기다린다.
- GIL은 `synchronized` 같은 자동 잠금이다.

첫 줄은 맞고 나머지는 반만 맞거나 틀렸다. 하나씩 따져 보니 출발점은 하나였다. 코어에 올라가는 단위는 프로세스가 아니라 스레드다.

## 코어에 올라가는 단위는 스레드다

| 단위 | 역할 |
|---|---|
| 코어 | 실제로 계산하는 하드웨어 |
| 프로세스 | 메모리 공간을 따로 가진 실행 단위. 다른 프로세스와 메모리를 공유하지 않는다 |
| 스레드 | 프로세스 안에서 실행되는 흐름. 같은 프로세스의 스레드끼리는 메모리를 공유한다 |

운영체제는 스레드를 코어에 배정한다. 프로세스는 스레드를 담는 그릇이라, 한 순간에 쓰는 코어 수는 그 순간 실제로 도는 스레드 수와 같다(최대 코어 수까지). 특정 코어에 붙어 있지도 않다. 한 스레드는 한 순간에 코어 하나만 쓰지만, 시간이 지나며 운영체제가 다른 코어로 옮긴다. 묶어 두려면 `taskset` 같은 도구로 일부러 고정해야 한다.

실제로 확인했다. 리눅스 서버(논리 코어 20개)에서 Python 프로세스 하나에 스레드 4개를 띄우고, 0.3초마다 각 스레드가 어느 코어에 있는지 `/proc` 에서 읽었다. 코드는 글 끝에 있다.

| 시각 | 스레드1 | 스레드2 | 스레드3 | 스레드4 |
|---|---|---|---|---|
| 0.3초 | 코어 0 | 코어 1 | 코어 3 | 코어 2 |
| 0.6초 | 코어 2 | 코어 0 | 코어 3 | 코어 1 |
| 0.9초 | 코어 0 | 코어 2 | 코어 3 | 코어 1 |
| 1.2초 | 코어 1 | 코어 2 | 코어 3 | 코어 0 |
| 1.5초 | 코어 2 | 코어 1 | 코어 0 | 코어 3 |
| 1.8초 | 코어 1 | 코어 3 | 코어 2 | 코어 0 |
| 2.1초 | 코어 3 | 코어 0 | 코어 1 | 코어 2 |

가로로 읽으면 매 시점 네 스레드가 서로 다른 코어 4개에 하나씩 있다. 프로세스 하나가 코어 4개를 동시에 썼다. 세로로 읽으면 스레드1은 코어 0, 2, 0, 1, 2, 1, 3으로 옮겨 다녔다. 같은 순간에 한 스레드가 코어 두 개를 쓴 적은 없다.

Python인데 네 스레드가 동시에 돈 것은 계산이 큰 데이터의 `sha256` 이었기 때문이다. 이 계산은 C 코드에서 GIL을 놓고 돈다. 순수 파이썬 반복문이었다면 스레드들이 각자 다른 코어에 올라가 있어도 GIL을 쥔 하나만 실행되고 나머지는 기다린다.

여기서 하나를 구분해 둔다. 병렬로 도는 이유는 스레드가 코어를 옮겨 다녀서가 아니라, 여러 스레드가 같은 순간에 각자 다른 코어에 있어서다. 스레드마다 코어를 하나씩 고정해도 병렬성은 그대로다.

프로세스나 스레드 수가 코어 수보다 많아도 된다. 같은 날 그 서버에는 코어 20개에 프로세스 561개, 스레드 2,291개가 떠 있었다. 운영체제가 짧은 간격으로 번갈아 돌린다. 기다리는 일(DB·네트워크 응답)이 많으면 코어보다 많이 띄우는 편이 이득이고, 계산만 하는 일이면 번갈아 돌 뿐이라 전환 비용과 메모리만 는다. "Python 프로세스는 코어 수만큼"이라는 말은 이 계산 위주의 경우를 두고 하는 말이다. Python 프로세스 하나가 파이썬 계산을 코어 1개 분량만 하니, 코어를 다 채우려면 그만큼 띄운다는 뜻이다. 코어 1개에 붙어 있다는 뜻은 아니다.

`top` 의 CPU 사용률로도 보인다. 100%가 코어 1개 분량이다. 100% 근처에서 더 안 오르는 Python 프로세스는 GIL에 막혀 있을 가능성이 높고, 400%인 프로세스는 코어 4개 분량을 동시에 쓰고 있다.

## 동시성과 병렬성

동시성(concurrency)은 한 기간 안에 여러 일을 번갈아 진행하는 것이다. 코어가 하나여도 된다. 병렬성(parallelism)은 같은 순간에 여러 일을 실제로 계산하는 것이다. 코어가 여러 개 있어야 하고, 동시에 실행되는 스레드나 프로세스도 여러 개 있어야 한다.

| 구성 | 동시성 | 병렬성 | 이유 |
|---|---|---|---|
| Tomcat, 프로세스 1, 코어 1 | 있음 | 없음 | 스레드들이 코어 하나를 번갈아 쓴다 |
| Tomcat, 프로세스 1, 코어 여러 개 | 있음 | 있음 | 스레드들이 여러 코어에서 동시에 돈다 |
| Uvicorn, 프로세스 1 | 있음 | 없음 | 이벤트 루프가 번갈아 처리하고, 파이썬 계산은 한 번에 하나다 |
| Uvicorn, 프로세스 여러 개, 코어 여러 개 | 있음 | 있음 | 루프와 GIL이 프로세스 수만큼 생긴다 |

Tomcat은 프로세스 하나와 코어 여러 개로 둘 다 얻는다. Uvicorn은 병렬성까지 얻으려면 프로세스가 여러 개 있어야 한다. "프로세스가 하나면 동시성이 없다"는 틀린 말이다. 없는 것은 병렬성이다.

## Tomcat: 요청 하나에 스레드 하나

Tomcat은 요청이 오면 스레드 풀(기본 최대 200개)에서 스레드를 하나 꺼내 맡긴다. 그 스레드는 요청을 처음부터 끝까지 순서대로 처리하고, DB를 부르면 응답이 올 때까지 멈춰 기다린다.

그래도 서버는 멈추지 않는다. 기다리는 건 그 요청 하나뿐이고 다른 요청은 다른 스레드가 맡는다. 기다리는 스레드는 코어를 놓고, 운영체제가 그 코어를 다른 스레드에 준다.

```
스레드 1 (요청 A): [계산][──── DB 대기 50ms ────][계산]
스레드 2 (요청 B):       [계산][── DB 대기 ──][계산]
스레드 3 (요청 C):             [계산][계산][계산]
코어 1:            [ A ][ B ][ C ][ C ][ B ][ A ]
```

기다림은 스레드가 하고 코어는 놀지 않는다. 기다리는 스레드가 차지하는 것은 메모리(스레드당 스택 약 1MB)다.

한계는 스레드가 전부 기다릴 때 온다. DB가 느려져 200개가 모두 응답을 기다리면 코어는 한가한데 새 요청에 줄 스레드가 없다. 새 요청은 대기열(기본 100개)에서 기다리고, 대기열까지 차면 연결이 거절된다.

Java에는 이 한계를 다루는 방법이 두 가지 있다. Spring WebFlux는 이벤트 루프 방식으로 바꾼다. Java 21의 가상 스레드는 코드를 그대로 두고 스레드를 가볍게 만들어, 기다리는 가상 스레드가 실제 스레드에서 내려와 자리를 비켜 준다. Spring Boot 3.2부터 `spring.threads.virtual.enabled=true` 로 켠다.

스레드가 메모리를 공유하는 데서 오는 비용도 있다. 같은 데이터를 두 스레드가 동시에 고치면 값이 꼬인다. 재고가 1개 남았을 때 두 요청이 동시에 "확인 후 차감"을 하면 둘 다 성공하고 재고는 -1이 된다. 개발자가 `synchronized`, 잠금, `ConcurrentHashMap` 등으로 직접 막아야 한다.

## Uvicorn: 스레드 하나의 이벤트 루프

Uvicorn은 Python ASGI 서버다. FastAPI 같은 async 앱을 실행하고, 요청을 받는 이벤트 루프가 스레드 하나에서 돈다.

DB나 네트워크 응답을 기다릴 때는 막히지 않는다.

```
스레드 1개: [A 처리][A: DB 요청 보냄, await]
                     [B 처리][B: DB 요청, await]
                                [C 처리]
                                   [A 응답 도착 → A 마무리]
                                      [B 응답 도착 → B 마무리]
```

`await` 를 만나면 응답이 오면 이어서 하도록 맡겨 두고 다음 요청으로 넘어간다. 스레드 하나로 요청 수천 개를 번갈아 진행할 수 있다.

CPU 계산에는 막힌다.

```
스레드 1개: [A 모델 추론 200ms ████████████████]
            B, C 는 이 200ms 동안 진행되지 않는다
```

계산 중에는 `await` 로 넘길 지점이 없다.

여기서 흔한 오해가 있다. 막히는 원인은 GIL이 아니라 스레드가 하나라는 점이다. GIL이 없는 언어라도 스레드 하나가 계산 중이면 다른 요청을 받지 못한다. GIL이 문제가 되는 것은 스레드를 늘리려 할 때다. 파이썬 계산은 스레드를 늘려도 한 번에 하나만 돌아서 소용이 없다. 그래서 Python은 스레드 대신 프로세스를 늘리는 쪽을 택했다. GIL은 막히는 원인이 아니라 해결 방법을 정한 원인이다.

해결은 두 가지다.

1. 계산을 다른 스레드에 넘긴다(`run_in_executor`, 스레드 풀). 루프는 계속 요청을 받는다. 계산이 C 코드라 GIL을 놓는 경우(numpy, PyTorch, OpenVINO 같은 추론 런타임)에만 병렬 효과가 있다.
2. 프로세스를 여러 개 띄운다. 루프와 GIL이 프로세스 수만큼 생긴다. `uvicorn --workers N` 이나 Gunicorn을 쓴다.

Gunicorn은 앱을 직접 실행하지 않는다. Uvicorn 워커를 여러 개 띄우고 죽으면 다시 띄우는 관리자다. 최근 Uvicorn은 `--workers` 로 여러 프로세스를 직접 관리할 수 있어서 Gunicorn 없이 쓰는 경우도 많다.

주의할 점이 하나 있다. `async def` 안에서 `await` 없는 동기 드라이버(`psycopg2`, `requests` 등)를 부르면, 응답 대기인데도 계산처럼 루프 전체가 멈춘다. FastAPI는 `async` 가 없는 일반 `def` 경로 함수를 스레드 풀에서 실행해 이 문제를 피한다.

## Nginx: 앱 코드를 실행하지 않는 앞단

Nginx는 Tomcat이나 Uvicorn과 같은 층이 아니다. 앱 코드를 실행하지 않고, 앞에서 요청을 받아 뒤로 넘긴다.

- HTTPS 암호화를 한 곳에서 푼다. 뒤쪽 서버는 평문만 다룬다.
- 이미지·JS 같은 정적 파일은 앱 서버까지 보내지 않고 바로 응답한다.
- 경로별로 다른 서버에 보내고, 같은 서버가 여러 대면 덜 바쁜 쪽으로 보낸다.
- 느린 업로드를 끝까지 받아 둔 뒤 한 번에 넘긴다. 앱 서버의 스레드나 워커가 느린 클라이언트에 붙잡히지 않는다.

C로 작성된 이벤트 방식 서버라 적은 메모리로 많은 연결을 유지한다. Java 서비스도 운영 환경에서는 보통 Nginx나 로드밸런서를 앞에 둔다. Python만의 구성이 아니다.

## 세 서버 비교

```
클라이언트
    ↓
  Nginx              앞단: SSL, 정적 파일, 요청 분배
    ↓
Tomcat 또는 Uvicorn   앱 서버: 코드 실행
    ↓
Spring 앱 / FastAPI 앱
```

| | Nginx | Tomcat | Uvicorn |
|---|---|---|---|
| 종류 | 웹 서버·리버스 프록시 | Java 앱 서버(서블릿 컨테이너) | Python 앱 서버(ASGI) |
| 작성 언어 | C | Java | Python |
| 실행하는 것 | 앱 코드는 실행하지 않음 | Spring 같은 Java 앱 | FastAPI 같은 async 앱 |
| 앱과의 규격 | 없음 (HTTP·gRPC로 넘김) | Servlet API | ASGI |
| 동시 처리 | 이벤트 루프 + 워커 프로세스 몇 개 | 요청당 스레드 하나 (기본 최대 200) | 이벤트 루프 하나 |
| 여러 코어를 쓰는 방법 | 워커 프로세스를 코어 수만큼 | 스레드가 여러 코어에서 동시에 | 프로세스를 여러 개 |
| 단독 외부 노출 | 원래 용도 | 가능하나 보통 앞에 프록시 | 공식 문서가 프록시 뒤 배포를 권함 |

## 헷갈리기 쉬운 점

- GIL은 `synchronized` 가 아니다. 인터프리터 내부만 보호한다. 여러 스레드가 `count += 1` 을 하면 Python에서도 값이 꼬일 수 있어 `threading.Lock` 이 필요하다.
- "Python은 스레드 병렬이 막혀 있다"는 반만 맞다. 막히는 것은 파이썬 코드 실행이고, I/O 대기와 C 코드 계산 중에는 GIL이 풀린다.
- Nginx는 빠른 Tomcat이 아니다. 하는 일이 다르다.
- 프로세스는 코어 하나에 고정되지 않는다. Python 프로세스가 쓰는 것은 파이썬 계산 기준 코어 1개 분량이다.
- GIL 없는 Python 빌드는 3.13에서 실험 기능으로 나왔고 3.14에서 공식 지원이 됐다. 기본 빌드에는 아직 GIL이 있다.

## 서빙에 적용할 때

모델 서빙 서버에서 프로세스를 늘릴지 스레드를 늘릴지는 [프로세스를 늘릴까, 스레드를 늘릴까](/posts/more-processes-or-more-threads/)에 정리했다. 요청 하나의 시간 중 네이티브 연산이 대부분이면 스레드로 코어를 채우고, 파이썬 구간이 천장이면 프로세스를 늘린다.

늘릴 때 같은 앱을 통째로 복제하는 Gunicorn식 구성과, 모델별로 프로세스를 떼어 내는 구성은 결과가 다르다. 통째 복제는 모든 모델이 프로세스 수만큼 메모리에 올라가고, 느린 모델 앞의 줄이 같은 프로세스 안의 빠른 모델까지 막는다. 모델별로 떼어 내면 프로세스마다 자기 모델만 올리고, 앞단 분배기가 호출 경로를 보고 나눠 보낸다. gRPC는 호출 이름이 `/패키지.서비스/메서드` 꼴의 경로라서 Nginx가 경로만으로 갈라 보낼 수 있다. 스레드 풀은 프로세스 안의 분배이고 Nginx는 프로세스 사이의 분배라서, 하나가 다른 하나를 대신하지 못한다.

## 메모

- 코어에 올라가는 단위는 스레드다. 프로세스가 쓰는 코어 수는 그 순간 도는 스레드 수다.
- Tomcat은 요청마다 스레드를 줘서 프로세스 하나로 동시성과 병렬성을 함께 얻는다. 한계는 스레드가 전부 기다릴 때 온다.
- Uvicorn은 이벤트 루프로 프로세스 하나에서도 동시성을 얻는다. 파이썬 계산의 병렬성은 프로세스를 늘려야 생긴다.
- Uvicorn이 계산에 막히는 원인은 스레드가 하나라는 점이고, GIL은 스레드 대신 프로세스를 늘리게 만든 원인이다.
- Nginx는 앱 서버 앞에서 SSL, 정적 파일, 분배를 맡는다. Tomcat과 Uvicorn이 같은 층이다.

## 실험 코드

```python
"""스레드 4개가 어느 코어에서 도는지 0.3초마다 찍는다."""
import hashlib
import os
import threading
import time

data = b"x" * (32 * 1024 * 1024)  # 큰 데이터 해시는 GIL 을 놓고 계산한다
stop = False


def work() -> None:
    while not stop:
        hashlib.sha256(data).digest()


ths = [threading.Thread(target=work) for _ in range(4)]
for t in ths:
    t.start()
pid = os.getpid()
tids = [t.native_id for t in ths]
snaps = []
for _ in range(7):
    time.sleep(0.3)
    row = []
    for tid in tids:
        with open(f"/proc/{pid}/task/{tid}/stat") as f:
            s = f.read()
        row.append(int(s[s.rfind(")") + 2:].split()[36]))  # 39번째 칸 = 지금 코어
    snaps.append(row)
stop = True
for t in ths:
    t.join()
print("시각    " + "  ".join(f"스레드{i+1}" for i in range(4)))
for i, row in enumerate(snaps):
    print(f"{(i+1)*0.3:.1f}초   " + "  ".join(f"코어{c:>3}" for c in row))
```
