## 같은 모델을 두 번 올리고 있었다

16GB GPU 한 장이 있는 공유 서버에서, 두 작업이 같은 4B급 모델로 데이터를 생성해야 했다. 한 작업은 transformers로 모델을 자기 프로세스에 4비트로 올려 여섯 건씩 묶어 생성하고 있었고, 그것만으로 10GB 남짓을 썼다. 다른 작업은 같은 모델을 하나 더 올릴 자리가 없었다.

속도도 문제였다. 고정 배치는 묶음 안에서 가장 긴 생성이 끝날 때까지 다음 묶음을 시작하지 못한다. 진행 속도로 계산하면 500건에 약 4시간이 걸릴 참이었다.

## vLLM이 하는 일

vLLM은 LLM 추론 서버다. 모델을 GPU에 한 번 올리고, OpenAI API와 같은 형식의 HTTP 엔드포인트로 요청을 받는다. 여러 프로세스가 같은 서버에 요청을 보내면 되므로 모델을 두 번 올릴 필요가 없다.

빠른 이유는 두 가지다. 연속 배치(continuous batching)는 요청이 들어오는 대로 진행 중인 배치에 끼워 넣고, 끝난 요청의 자리를 바로 다음 요청으로 채운다. 가장 긴 생성을 기다리며 GPU가 노는 시간이 없어진다. PagedAttention은 생성 중의 KV 캐시를 작은 페이지 단위로 나눠 관리해서, 요청마다 최대 길이만큼 메모리를 미리 잡아 두는 낭비를 줄인다. 같은 메모리로 더 많은 요청을 동시에 처리한다.

## 설치는 따로 했다

vLLM 최신 버전은 학습 환경보다 새 버전의 PyTorch를 요구했다. 학습용 가상환경에 설치하면 학습 코드가 쓰는 PyTorch가 바뀐다. 서빙용 가상환경을 따로 만들어 설치했다. 용량은 8GB 정도였다. 서버는 그 환경에서 띄우고, 클라이언트는 HTTP만 쓰니 어느 환경에서 호출해도 된다.

모델은 양자화 인지 학습(QAT)으로 만든 4비트 가중치판을 썼다. vLLM이 이 형식을 그대로 읽어서 가중치 로딩이 7초 걸렸다. 사내망 환경이라 허브 접속을 끄고(`HF_HUB_OFFLINE=1`) 로컬 캐시만 읽게 했다.

## 메모리 설정

`--gpu-memory-utilization`은 서버가 GPU 전체 메모리 중 얼마까지 쓸지 정한다. 0.85로 두니 가중치와 실행 그래프를 뺀 나머지 1.4GB 정도가 KV 캐시로 잡혔고, 약 3만 7천 토큰 분량이었다. 최대 길이 8K 요청이면 동시에 4~5개지만, 실제 요청은 대부분 그보다 짧아서 동시 요청 16개가 무리 없이 돌았다. 남은 15% 정도는 다른 작업이 쓸 여유로 남겼다.

## 결과

멀티턴 대화 1,000건을 재시도까지 포함해 약 23분에 생성했다. 고정 배치로 계산했던 4시간과 비교하면 한 자릿수 배 이상 빨랐다. 구조화 출력(JSON 스키마로 출력 형식 강제)도 서버 기능으로 바로 쓸 수 있었다. 다른 작업도 같은 엔드포인트를 쓰면 되므로, 모델을 각자 올리느라 GPU를 다툴 이유가 없어졌다.

## 운영할 때 주의한 점

- 서버는 떠 있는 동안 설정한 비율만큼 GPU 메모리를 잡고 있다. 쓰는 사람이 없으면 다른 GPU 작업을 막는다. 엔드포인트를 공유하고, 한동안 쓰지 않으면 내린다.
- 서버를 백그라운드 서비스로 띄우고, 이를 쓰는 파이프라인은 시작할 때 헬스 체크(`/health`)부터 한다. 서버가 없으면 생성 단계로 넘어가지 않고 바로 실패 상태를 남긴다.
- 프로세스 안에서 4비트로 올린 모델과 QAT 가중치를 서빙하는 모델은 출력이 완전히 같지 않다. 같은 모델명이라도 어느 쪽으로 생성했는지 기록에 남긴다.

## 정리

여러 작업이 같은 모델로 추론해야 하면 각자 올리지 말고 서버 하나에 올려 나눠 쓴다. vLLM은 연속 배치와 페이지 단위 KV 캐시로 같은 GPU에서 처리량을 크게 올리고, OpenAI 호환 API라 클라이언트도 간단하다. 학습 환경과 의존성이 충돌하면 서빙 환경을 분리하고, 서버가 GPU를 점유한다는 점은 공유 환경에서 항상 의식한다.
