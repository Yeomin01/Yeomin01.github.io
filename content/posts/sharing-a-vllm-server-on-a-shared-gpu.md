## 모델이 올라가지 않았다

평가용 문서 생성을 다시 돌리려는데 로컬 4B 모델이 GPU 메모리 부족으로 올라가지 않았다. 직전까지는 GPU가 비어 있었다.

확인 순서는 이랬다.

1. `nvidia-smi`로 GPU 전체와 프로세스별 사용량을 봤다. 16GB 중 13.8GB를 프로세스 하나가 쓰고 있었다.
2. 그 프로세스의 부모를 따라 올라가 실행 명령을 확인했다. vLLM 서버였고, 내가 쓰려던 것과 같은 계열의 4B 모델을 OpenAI 호환 API로 서빙하고 있었다. `--gpu-memory-utilization 0.85`로 떠 있어 남은 메모리는 2GB 남짓이었다.
3. 서버 로그와 접속 중인 클라이언트를 확인했다. 다른 생성 작업이 동시 요청 16개로 이 서버를 쓰고 있었고, 그 작업의 진행 로그로 끝나는 시점도 대략 가늠할 수 있었다.

## 하지 않은 것

내가 띄운 프로세스가 아니었으므로 정리하지 않았다. 공유 서버에서 남의 프로세스를 소유자 확인 없이 끝내면, 그 사람의 몇 시간짜리 작업이 사라질 수 있다.

GPU가 비면 자동으로 시작하는 대기 스크립트도 만들지 않았다. 예전에 그런 대기 장치가 남아 있다가, 사용자가 기다리라고 한 뒤에 혼자 작업을 시작해 GPU를 15GB 넘게 잡은 일이 있었다. 같은 GPU를 쓰는 다른 사람의 작업이 메모리 부족으로 죽을 수 있는 상태였다. 그 뒤로 GPU를 쓰는 작업은 시작하라고 한 시점에만 시작한다.

그래서 상황을 그대로 보고하고 선택지를 물었다. 그 작업이 끝날 때까지 기다릴지, 서버를 같이 쓸지였다.

## 같은 모델이면 서버를 같이 쓴다

서버가 띄운 모델이 내가 쓰려던 모델과 같은 계열이었고, 사용 허락도 받았다. 그래서 내 프로세스에 모델을 한 번 더 올리는 대신 그 서버에 요청을 보내기로 했다. 생성 코드는 이미 OpenAI 호환 인터페이스로 백엔드를 갈아 끼울 수 있게 되어 있어서, 백엔드 하나를 추가하는 것으로 끝났다.

| | 직접 올림 (transformers, 4bit) | 서버 공유 (vLLM) |
|---|---|---|
| 추가 GPU 메모리 | 수 GB 필요 (올라가지 않음) | 0 |
| 처리 속도 | 명세 1건당 약 5초 | 완료 1건당 약 1.6초 (동시 12) |

동시 요청 수는 다른 작업의 부하를 보며 정했다. 다른 작업이 돌 때는 6개로 붙였다. 그때 서버 로그의 KV 캐시 사용률은 55~65%였다. 다른 작업이 끝난 것은 프로세스 생사가 아니라 그 작업의 상태 파일에 기록된 완료 표시로 확인했고, 그 뒤에 12개로 올렸다. 서버 하나에 요청이 몰리면 서로 느려질 뿐 메모리가 더 들지는 않는다. vLLM은 시작할 때 KV 캐시를 미리 잡아 두기 때문이다.

## 언제든 멈추고 다시 돌릴 수 있게

공유 자원을 쓰는 작업은 중간에 멈출 일이 생긴다. 다른 사람이 GPU를 써야 할 수도 있고, 내가 코드를 고쳐야 할 수도 있다. 그래서 생성 작업은 다음처럼 만들었다.

- 문서 ID마다 시드를 고정해, 같은 ID는 언제 다시 돌려도 같은 명세로 생성한다.
- 결과는 한 줄 쓸 때마다 flush 하고, 다시 시작하면 이미 저장된 ID는 건너뛴다.
- 5분 넘게 걸리는 작업은 `setsid`로 터미널과 분리해 띄우고, 로그는 파일로 남긴다.
- 강제로 멈춘 뒤에는 마지막 줄이 온전한지, 중복 ID가 없는지 확인하고 이어서 돌린다.

실제로 이 작업은 두 번 멈췄다. 한 번은 검사 로직의 버그를 고칠 때, 한 번은 다른 작업이 끝나 동시성과 명세 수를 함께 올릴 때였다. 매번 저장된 결과는 그대로 두고 남은 ID만 이어서 생성했다.

## 프로세스를 이름으로 찾다가 내 셸을 죽였다

동시성을 올리려고 내 생성 프로세스를 멈추는 과정에서 실수가 있었다. 이렇게 했다.

```bash
for pid in $(pgrep -f "build_dev --backend vllm"); do kill $pid; done
```

`pgrep -f`는 전체 명령줄에서 패턴을 찾는다. 이 명령을 실행하는 셸 자신의 명령줄에도 같은 문자열이 들어 있다. 그래서 생성 프로세스와 함께 내 셸도 목록에 들어갔고, 스스로를 종료했다(종료 코드 144). 이어서 실행하려던 재시작 명령은 돌지 않았다.

그 뒤로는 프로세스를 이름으로 찾아 죽이지 않는다. 띄울 때 PID를 기록하거나, `ps` 출력에서 실행 파일 필드까지 확인해 정확한 PID를 고른 다음 그 PID만 종료한다. 끝났는지 기다릴 때도 패턴 대신 `kill -0 <PID>`로 그 PID가 살아 있는지만 본다.

```bash
ps -eo pid,args | awk '$2 ~ /python3/ && /--backend vllm/ {print $1}'
while kill -0 "$PID" 2>/dev/null; do sleep 20; done
```

## 정리

공유 GPU에서 메모리가 부족할 때 먼저 할 일은 그 메모리를 누가 왜 쓰는지 확인하는 것이다. 남의 프로세스는 건드리지 않고, 자동으로 자원을 잡는 장치도 두지 않는다. 같은 모델이 이미 서빙 중이면, 따로 올리는 것보다 그 서버를 같이 쓰는 편이 메모리와 처리량 모두에서 낫다. 그리고 공유 자원을 쓰는 작업은 언제든 멈추고 이어서 돌릴 수 있게 만든다.
