## 후보를 하나씩 시도했다

평가용 문서를 수백 건 생성해야 했다. 생성기는 두 종류를 섞기로 했다. 문체가 한 모델에 쏠리지 않게 하려는 것이다. 후보는 직접 호출하는 상용 API 몇 개, 클라우드의 관리형 모델 서비스, 로컬 GPU에서 띄우는 오픈 모델이었다.

모델을 비교하기도 전에 접근 단계에서 차례로 막혔다.

| 후보 | 결과 | 원인 |
|---|---|---|
| 상용 API A | 인증 실패 | 환경에 들어 있던 키가 유효하지 않았다 |
| 클라우드 관리형 서비스 | 403 / 404 | 계정에서 해당 모델 접근이 활성화돼 있지 않았다 |
| 상용 API B | 429 | 크레딧이 없었다 |
| 국내 모델 API | 성공 | OpenAI 호환 엔드포인트 |

클라우드 관리형 서비스는 계정이 있다고 바로 모든 모델을 부를 수 있는 게 아니다. 모델마다 접근을 활성화해야 하고, 일부 제공사 모델은 사용 목적 양식을 제출해야 한다. 승인 전에는 존재하는 모델 ID로 불러도 403이나 404가 돌아온다. 오류 메시지만 보면 모델 이름을 잘못 쓴 것처럼 보이기도 한다.

정리하면, 백엔드를 정할 때 먼저 확인할 것은 성능표가 아니라 키의 유효성, 모델 접근 승인, 쿼터와 결제 상태였다. 이 셋 중 하나라도 막히면 다른 비교는 의미가 없다.

## OpenAI 호환 인터페이스로 갈아 끼운다

결국 쓴 두 백엔드는 국내 모델 API와 로컬 오픈 모델이었다. 둘 다 OpenAI 호환 인터페이스로 묶었다.

```python
from openai import OpenAI

api   = OpenAI(api_key=os.environ["VENDOR_API_KEY"], base_url=VENDOR_BASE_URL)
local = OpenAI(api_key="EMPTY", base_url="http://localhost:8000/v1")  # vLLM

r = client.chat.completions.create(model=MODEL, messages=msgs, max_tokens=3000)
```

`base_url`과 모델 이름만 바꾸면 같은 생성 코드가 돈다. 처음에는 로컬 모델을 transformers로 직접 올려 `generate`를 호출했는데, 나중에 같은 모델을 vLLM으로 서빙하는 쪽으로 바꿀 때 생성 코드는 고칠 필요가 없었다. 백엔드 선택을 명령행 인자 하나로 두고, 레코드마다 어느 백엔드와 어느 구현으로 만들었는지 남겼다.

모델마다 다른 점도 이 층에서 흡수했다. 로컬 모델(gemma 계열)은 채팅 템플릿에 system 역할이 없어서, 시스템 지시를 첫 user 메시지 앞에 붙여 보낸다. transformers로 부를 때도 vLLM으로 부를 때도 같은 규칙이다.

## 처리량은 구현에 따라 크게 달랐다

같은 4B 모델이라도 부르는 방식에 따라 처리량이 크게 달랐다.

| 방식 | 대략의 처리 속도 |
|---|---|
| transformers + 4bit 양자화, 6건 배치 `generate` | 명세 1건당 약 5초 |
| vLLM 서빙(4bit), 동시 요청 12개 | 완료 1건당 약 1.6초 |
| 상용 API, 동시 요청 6개 | 완료 1건당 약 2초 |

`generate` 배치는 배치 안에서 가장 긴 출력이 끝날 때까지 다른 요청이 기다린다. 서빙 엔진은 요청 단위로 들어오고 나가며 KV 캐시를 나눠 쓴다. 출력 길이가 제각각인 문서 생성에서는 이 차이가 그대로 처리량 차이가 된다. 같은 16GB GPU, 같은 모델로 낸 차이다.

## 키는 환경 파일로만 다룬다

API 키는 코드와 설정 파일, 로그 어디에도 쓰지 않는다. 저장소에 올라가지 않는 환경 파일에만 두고, 예시 파일에는 키 이름만 적는다. 생성 코드는 실행할 때 환경 파일을 읽는다.

작은 문제가 하나 있었다. `python-dotenv`의 `load_dotenv()`는 경로를 주지 않으면 호출한 코드의 파일 위치를 기준으로 `.env`를 찾는다. 표준 입력으로 넘긴 코드처럼 파일이 없는 실행 환경에서는 그 탐색이 실패한다. 경로를 명시해 `load_dotenv(".env")`로 부르면 실행 방식과 상관없이 같은 파일을 읽는다.

로그에도 주의했다. 실패한 요청을 디버깅하면서 클라이언트 설정이나 헤더를 통째로 출력하면 키가 로그에 남는다. 오류는 예외 종류와 상태 코드만 기록했다.

## 정리

LLM 백엔드를 고를 때 가장 먼저 막힌 것은 모델 성능이 아니라 접근이었다. 키 유효성, 클라우드 모델 접근 승인, 쿼터를 먼저 확인한다. 백엔드는 OpenAI 호환 인터페이스로 묶어 두면 API와 로컬 서빙을 같은 코드로 바꿔 쓸 수 있다. 로컬 모델은 직접 `generate`를 부르기보다 서빙 엔진에 올리는 편이 처리량이 훨씬 좋았다.
