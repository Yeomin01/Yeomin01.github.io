## 이어서

레드팀 데이터를 라벨 분포가 아니라 **방향**으로 세어봤다. PII가 어느 쪽 발화에 들어 있나.

```
챗봇 응답에 등장   86%
사용자 입력에 등장 10%
```

우리가 만든 시나리오가 전부 "챗봇에게서 정보를 빼낸다"였으니 당연한 결과다. 그런데 실제 배포에서 더 흔한 경로는 반대쪽이다. 직원이 고객 명단을 붙여넣고 "표로 정리해 줘"라고 하는 쪽.

그 축이 데이터에 거의 없었다. 없으니 재본 적도 없었다.

## 반대 방향을 만들었다

사용자가 PII를 들고 들어오는 시나리오를 48대화 만들었다. 17개 라벨로 288건을 심었고, 그중 238건이 실제 사용자 발화에 렌더링됐다.

가드에 통과시킨 결과는 이랬다.

```
유출된 PII        238건
가드가 놓침         38건
  그중 누적형       31건
  단일 메시지 미탐    7건 (전부 이름)
```

38건을 그대로 미탐률로 쓰면 16%다. 그런데 31건은 **여러 턴에 나눠 들어와 누적으로만 성립**하는 건이다. 메시지 단위로 스캔하는 배포 구조에서는 원리상 못 잡는다. 이건 탐지 성능이 아니라 배포 형태의 결과다.

그걸 빼면 200/207, 96.6%다. 남은 7건은 전부 이름이고, 이름은 문맥 판단 단계가 따로 맡는데 이번 측정에서는 그 단계를 끄고 돌렸다.

**"못 잡음"을 보고하기 전에 "구조상 못 잡음"과 "잡을 수 있었는데 놓침"을 갈라야 한다.** 안 가르면 고칠 수 없는 것을 고치려 들게 된다.

## 없던 표면이 나왔다

여기서 예상 못 한 게 하나 나왔다. 챗봇이 사용자가 준 값을 **응답에 되풀이한다.**

```
사용자가 준 값이 챗봇 응답에 다시 등장   75건
  그중 가드가 놓친 것                  10건
  카드번호                             2건
```

사용자가 자기 정보를 넣었고, 그게 모델 응답을 타고 다시 나온다. 로그·화면·다음 턴의 컨텍스트로 퍼진다. 원래 시나리오에서는 챗봇이 **시스템 프롬프트에 있던** 값을 흘리는 것만 봤으니, 이 경로는 관측 자체가 안 되고 있었다.

## 넓게 보면

위협 모델은 문서에 적히는 게 아니라 **데이터 분포에 새겨진다.** 우리가 만든 시나리오의 모양이 곧 우리가 방어를 재는 범위였다. 만들지 않은 축은 못 재고, 못 재는 것은 지표상 존재하지 않는다. 0%가 아니라 아예 칸이 없는 것이다.

그래서 레드팀 데이터를 볼 때 라벨 분포만 보면 안 된다. **누가 말했나, 어디서 흘러 들어왔나, 어디로 나가나**를 축으로 세어보면 비어 있는 칸이 보인다. 그 칸이 실제 서비스에서 얼마나 흔한지가 다음 작업의 우선순위다.

여기서는 비어 있던 칸이 실제로는 더 흔한 경로였고, 그 칸을 채우자 기존 데이터로는 존재조차 몰랐던 유출 경로가 같이 나왔다.

## 메모

- 레드팀 데이터를 라벨이 아니라 방향으로 센다. 어느 발화에 PII가 있는지 세어보면 시나리오가 만든 사각지대가 드러난다.
- 미탐을 보고하기 전에 구조상 불가능한 건을 분리한다. 메시지 단위 스캐너에서 턴에 흩어진 값은 성능 문제가 아니다.
- 사용자가 넣은 PII가 모델 응답으로 되돌아 나오는 경로를 따로 센다. 입력만 막으면 이 경로는 그대로 열려 있다.
