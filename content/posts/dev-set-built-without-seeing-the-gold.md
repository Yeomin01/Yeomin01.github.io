## 왜 따로 만들었나

평가용 골드셋의 미탐을 보고 학습 데이터를 만들었다가 골드셋을 틀·어휘 단위로 오염시킨 일이 있었다. 그 뒤로 역할을 나눴다. 골드셋은 최종 보고에만 쓴다. 모델이 무엇을 놓치는지 찾는 갭 분석은 골드셋과 독립적으로 만든 dev 셋으로 한다. dev 셋의 미탐을 보고 학습 데이터를 만들면 dev 셋은 다음 모델에 대해 오염되지만, 그건 괜찮다. 다음 라운드에 새 dev 셋을 만들면 된다. 지켜야 하는 것은 골드셋 하나다.

대상은 사내 업무 문서였다. 직원이 업무용 챗봇에 문서를 붙여넣고 요약이나 번역을 요청하는 입력이다.

## 정답은 구조로 보장한다

처음에는 생성기가 이름·기관명은 직접 쓰고 `[[NAME:값]]`으로 감싸게 했다. 시범 6건에서 생성기는 전화번호 같은 자리표시자는 다 지키면서, 자기가 지어낸 이름은 감싸지 않았다. 정답에서 이름이 빠지면 그 자리는 잴 수 없게 된다.

그래서 모든 개인정보를 자리표시자로만 쓰게 바꿨다. 생성기는 `[[NAME]]`, `[[ORG:은행]]`, `[[AMOUNT:급여]]`, `[[RRN]]` 같은 자리만 만들고, 값은 코드가 채운다. 값을 채우는 순간 위치를 알기 때문에 정답 스팬이 생성기의 판단과 무관하게 정확해진다.

값은 이렇게 채웠다.

- 실존 금융사·통신사·공공기관·병원은 닫힌 목록에서 고른다.
- 사람 이름·회사명·주소·금액은 무작위로 합성한다.
- 주민번호·카드번호·사업자번호처럼 체크섬이 있는 식별자는 운영 중인 검증기를 직접 통과한 난수만 쓴다.
- 같은 사람은 `[[NAME#1]]`처럼 번호로 묶어 같은 이름을 채운다.

## 생성기는 둘을 섞었다

API로 쓰는 대형 모델과 로컬에서 띄운 4B 모델을 절반씩 썼다. 문체가 한 생성기에 쏠리지 않게 하려는 것이다. 한계도 있다. 로컬 4B 모델은 운영 중인 2차 검증 모델과 같은 계열이라, 2차 단계를 dev 셋으로 재면 자기가 쓴 문장을 판정하는 셈이 된다. 1차 모델의 갭 분석에는 영향이 없다. 이 점은 데이터 설명서에 적어 뒀다.

## 무엇이 부족한지는 학습셋으로 정했다

갭 분석용 셋이니 모델이 약할 법한 곳을 넉넉히 담아야 한다. 그런데 어디가 약한지를 골드셋 미탐으로 정하면 같은 오염이 반복된다. 그래서 "무엇이 부족한가"는 학습셋 분포와, 먼저 만든 절반의 분포로만 정했다.

| 항목 | 학습셋 |
|---|---|
| 길이 중앙값 | 38자 |
| 600자 이상 | 0.3% |
| 코드·로그가 섞인 문서 | 0.0% |
| 영어 문서 | 0.3% |
| 금액 값 상위 20개가 차지하는 비율 | 23.9% |

먼저 만든 절반에서는 이름·기관명·전화·이메일이 스팬의 87%였고, 여권번호는 2개, 운전면허번호는 4개뿐이었다. 생성기는 시키지 않으면 흔한 개인정보만 쓴다.

나머지 절반은 부족한 쪽을 겨냥한 명세로 만들었다. 희귀 라벨 하나를 반드시 넣게 하고, 그 라벨이 자연스럽게 나오는 업무 상황을 같이 준다. 해외 출장 서류에는 여권번호, 법인카드 정산에는 카드번호, 보안 사고 보고에는 IP 주소다. 문서 형태에 로그·설정 파일·코드 조각을 15%, 언어에 영어를 15% 넣었다. 값 목록도 넓혔다. 복성과 드문 성씨, 외자 이름, 외국인 이름, 지번·영문 주소, 한글 금액(금 일천오백만원정)과 외화 표기를 추가했다.

## 재현성

생성 파이프라인은 학습 파이프라인처럼 다시 돌릴 수 있게 만들었다.

- 문서 ID마다 시드를 고정했다. 명세를 뽑는 난수와 값을 채우는 난수를 분리해서, 재시도로 값이 바뀌어도 명세는 그대로다.
- 결과는 한 줄씩 써서 바로 flush 하고, 다시 실행하면 이미 있는 ID는 건너뛴다. 중간에 멈추거나 코드를 고쳐 다시 돌려도 거부됐던 ID만 다시 생성한다.
- 레코드마다 생성기, 구현(로컬 양자화 / 서빙 엔진), 명세 종류를 남겼다.
- 품질 검사는 생성 시점에 한 번, 병합 시점에 한 번 더 건다. 병합 단계는 지금 있는 검사를 전부 다시 적용하므로, 나중에 추가한 검사도 이전 산출물에 소급된다. 실제로 먼저 만든 479건 중 152건이 나중에 추가한 검사로 빠졌고, 빠진 몫은 부족분 명세로 다시 채웠다.
- 폴더에 데이터 설명서를 두었다. 맨 위에 "학습 투입 금지, 성능 보고에 쓰지 않음"을 적고, 만든 방법과 알려진 한계, 감사 결과를 남겼다.

| 정답 스팬 | 12,533 |

| 표·명단 / 로그·코드 | 96 / 96 |

## 누출 감사는 두 방향으로 했다

골드셋 대비 감사는 골드셋 오염 여부를 본다. dev 셋이 골드셋을 닮으면, dev 셋의 미탐을 보고 만든 학습 데이터가 다시 골드셋을 오염시킨다. 업무 문서 축의 틀 공유는 전부 0%였다. 어휘 일치가 높은 축이 있었지만 겹친 값은 실존 기관명, 흔한 이름, 일반 부서명뿐이었다. 예외가 하나 있었다. 한 축의 골드셋 400턴이 전부 "이름 / 주민번호 / 연락처" 순서의 같은 서식을 갖고 있었고, dev 문서 1건이 우연히 같은 순서를 썼다. 그 축은 100% 공유로 잡혔다. 생성기는 골드셋을 본 적이 없으니 우연이고, 학습셋에는 그 틀이 없었다. 이 문서는 학습 데이터 생성에 쓰지 않도록 표시했다. 한 서식으로 만든 골드셋 축은 흔한 서식 하나에도 100%가 된다는 점은 골드셋을 다음 버전으로 만들 때 반영할 일로 남겼다.

학습셋 대비 감사는 측정력을 본다. dev 셋이 학습셋을 닮으면 일반화를 잴 수 없다. 갈래별로 문서의 8~15%가 학습셋과 틀을 하나 이상 공유했다. 먼저 만든 절반 기준으로 공유한 틀은 56개뿐이었고 전부 "이름 - 연락처: 번호" 같은 필드 나열 서식이었다. 특정 템플릿을 다시 쓴 흔적은 없었다.

## 남은 일

정답을 점검하다가 생성기가 문맥 의존 라벨에 과다 라벨을 붙인 것을 발견했다. 특정 개인과 묶이지 않은 기관명·주소·금액에도 자리표시자를 썼다. 이 부분은 스팬마다 결합 여부를 판정하는 단계를 더해 바로잡을 계획이고, 그 전까지 세 라벨은 갭 분석에 쓰지 않는다. 자세한 내용은 [정답에서 빠진 것과 정답에 잘못 들어간 것은 무게가 다르다](/posts/missing-and-wrong-labels-weigh-differently/)에 정리했다.

## 정리

평가용 데이터를 만드는 일도 학습 데이터 파이프라인과 같은 기준으로 다뤘다. 시드와 ID로 다시 만들 수 있어야 하고, 검사는 산출물 전체에 다시 적용할 수 있어야 하고, 무엇으로 만들었는지가 레코드와 설명서에 남아야 한다. 그리고 갭 분석용 셋은 무엇을 담을지 정하는 단계부터 평가셋을 보지 않아야 한다.
