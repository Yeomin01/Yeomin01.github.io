PII 가드는 입력으로 받은 텍스트에서 개인정보를 탐지해 마스킹 여부를 결정하는 BERT NER 기반의 보안 레이어다. 게이트웨이에서 부르고, 게이트웨이가 결과를 받아 후속 처리 (마스킹·차단·통과) 를 결정한다. 그 호출 인터페이스 양쪽을 두 갈래로 정제하기로 했다.

## 입력 — 글 전체가 아니라 문장 단위 리스트

기존에는 사용자가 입력한 글을 통째로 PII 레이어에 넘기고, 그 안에서 형태소 분석기 (kiwi) 로 토큰을 잘라서 NER 에 태웠다. 이 흐름의 문제가 두 가지 있다.

첫째, NER 의 entity 는 거의 항상 한 문장 안에 닫힌다. 이름, 전화번호, 주민등록번호, 주소처럼 PII 로 잡히는 표현은 다른 문장으로 흘러넘치지 않는다. 그런데 글 전체를 한 번에 토큰 시퀀스로 만들면, 모델이 처리할 컨텍스트의 절반 이상은 entity 와 무관한 다른 문장이 된다. 노이즈가 많은 만큼 긴 시퀀스 처리 비용은 오르고, 가끔은 다른 문장의 단어가 ORG·NAME 같은 라벨로 잘못 끌려가기도 한다.

둘째, BERT 의 max_length (보통 512) 를 글 전체가 자주 넘는다. 넘어가는 분은 truncate 되거나 sliding window 로 분할되는데, 두 방식 모두 entity 가 boundary 에 걸리면 잘리기 쉽다. 한 사람의 주소가 두 윈도우에 나뉘면 한쪽은 누락되고 한쪽은 절반만 잡힌다.

문장 단위로 자르면 두 문제가 같이 풀린다.

```python
# 기존
result = pii_layer(text)              # text = 글 전체

# 변경
sentences = split_sentences(text)
results = pii_layer(sentences)        # [s1, s2, ...] 리스트로 호출
```

문장 분리는 형태소 분석보다 가벼운 작업이고 ([. ?! 줄바꿈 + 한국어 종결어미] 정도로 충분), 결과 리스트는 원본 글의 문장 순서를 그대로 보존한다. 게이트웨이가 결과를 받아 다시 글로 합칠 때는 문장 인덱스만 따라가면 된다.

문장 단위 호출의 다른 이점은 캐싱이다. 같은 사용자가 같은 문장을 반복해서 보내는 경우 (시스템 프롬프트, 자주 쓰는 표현) 가 적지 않은데, 문장 단위면 해시 키가 짧아 캐시 hit 율이 올라간다.

## 출력 — on/off 가 아니라 분류 + 임계값 + reasoning

PII 가 잡혔는지 / 안 잡혔는지의 2진 답만 돌려주면 게이트웨이가 할 수 있는 게 별로 없다. 마스킹할지, 통과시킬지, 차단할지의 정책은 단지 detection 자체보다 더 세밀한 입력이 필요하다.

- 어떤 카테고리가 잡혔는지 (이름인지, 주민등록번호인지, 외국 회사명인지)
- 모델이 얼마나 확신하는지 (logit, 또는 calibrated probability)
- 왜 그렇게 분류했는지 (해당 토큰의 컨텍스트, 매칭된 패턴, 사전 명단의 어느 항목인지)

이 세 가지가 같이 나오면 게이트웨이가 정책별로 처리할 수 있다. 예를 들어 같은 ORG 라벨이라도

- "이재용" + reasoning "DART 비상장 외감 명단 + ORG 컨텍스트" — 마스킹
- "LG전자" + reasoning "DART 상장사 명단 매칭 — public_negative" — 통과
- "포레스트병원" + reasoning "인허가 사업장 + ORG suffix 매칭" — 마스킹

으로 분기가 다르다. 모델이 "ORG 잡혔음 / 안 잡혔음" 만 돌려주면 이 분기를 못 만들고, 게이트웨이가 다시 사전 매칭을 돌려야 한다. 이미 모델 추론 단계에서 가진 정보를 두 번 계산하는 셈이다.

같은 카테고리라도 임계값을 둘 수 있다. 학습된 PII NER 의 confidence 가 0.95 인 토큰과 0.55 인 토큰은 다르게 다뤄야 한다. 게이트웨이가 보수적 정책을 쓰면 0.55 도 마스킹하지만, 진보적 정책에서는 0.85 이하는 통과시킨다. 모델이 임계값을 일률적으로 적용해서 "잡혔다 / 안 잡혔다" 만 돌려주면 이 조정 여지가 사라진다.

reasoning 의 형식은 자유롭지만, 최소한 다음 정보가 들어가야 게이트웨이가 쓸 수 있다.

```json
{
  "text": "포레스트병원",
  "label": "ORG",
  "confidence": 0.93,
  "reasoning": {
    "matched_pattern": "한글 1~6자 + 병원",
    "list_hit": "localdata_health",
    "context": "포레스트병원에서 진료받았다"
  }
}
```

## 두 변경의 책임 경계

이 두 변경에서 모델과 게이트웨이의 역할이 분리된다.

- 모델은 입력 문장 안에서 PII 후보를 식별하고, 카테고리 + confidence + 분류 근거를 돌려주는 데 집중한다.
- 게이트웨이는 받은 결과를 정책 (사용자 권한, 도메인, 컨텍스트) 과 합쳐서 최종 처리를 결정한다.

이전에는 모델이 임계값까지 일률 적용해 단순 detection 결과만 돌려주고, 게이트웨이는 단순 on/off 로 동작했다. 그래서 정책을 바꿀 때 모델을 다시 학습시켜야 했다. 새 구조는 모델 학습은 그대로 두고 임계값·정책만 게이트웨이에서 바꿔도 동작이 달라진다.

## 정리

PII 가드의 호출 인터페이스에서 양 끝을 손봤다. 입력은 글 전체에서 문장 리스트로 가벼워졌고, 출력은 단순 detection 에서 카테고리 + confidence + reasoning 로 풍부해졌다. 두 변경 모두 모델과 게이트웨이의 역할을 명확히 분리하기 위한 작업이다. 분류는 모델, 정책은 게이트웨이 — 그 경계를 인터페이스 자체에 반영했다.
