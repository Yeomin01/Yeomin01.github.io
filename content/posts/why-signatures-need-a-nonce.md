## 이어서

외부에 API 를 열 때 인증 규격을 읽다가, 서명과 논스가 왜 **둘 다** 필요한지가 한 번에 안 들어왔다. 서명이 있으면 위조를 막는 것 아닌가 싶었는데, 막는 대상이 서로 달랐다.

## 서명은 '내용이 바뀌었는가'를 본다

보내는 쪽과 받는 쪽이 **같은 비밀키**를 나눠 갖는다. 보내는 쪽은 요청 내용에 그 키를 섞어 짧은 값을 뽑아 함께 보낸다(HMAC). 받는 쪽은 도착한 내용으로 같은 계산을 해서 두 값을 비교한다.

![요청 내용을 바꾸면 서버가 다시 계산한 서명과 어긋나 거절된다](/images/hmac_signature.svg)

중간에서 누가 금액을 바꿔도, **바뀐 내용에 맞는 서명은 못 만든다.** 비밀키가 없으니까. 그래서 서버가 다시 계산하면 값이 어긋나고 거절된다.

여기서 서명 대상에 **무엇을 넣느냐**가 중요하다. 본문만 서명하고 경로나 메서드를 빼면, 같은 본문을 다른 엔드포인트로 돌려보내는 게 통과한다. 실무 규격들이 `메서드 + 경로 + 타임스탬프 + 본문해시`를 묶어 서명하는 이유다.

## 논스는 '이미 본 요청인가'를 본다

문제는 서명이 **내용에만** 걸린다는 점이다. 공격자가 정상 요청을 통째로 복사해 그대로 다시 보내면, 내용이 안 바뀌었으니 **서명도 여전히 유효하다.** 송금 요청이 두 번 처리된다.

![서명이 유효해도 같은 논스가 두 번 오면 재전송으로 보고 거절한다](/images/hmac_nonce.svg)

그래서 요청마다 **한 번만 쓰는 임의값**(논스)을 붙이고 그것까지 서명에 포함한다. 받는 쪽은 본 논스를 적어두고, 같은 값이 또 오면 서명이 맞아도 거절한다.

논스를 영원히 기억할 수는 없으니 보통 **타임스탬프와 함께** 쓴다. "5분 이내 요청만 받는다"로 창을 좁히고, 그 창 안의 논스만 저장한다. 그러면 저장소가 유한해진다. 대신 서버 간 시계가 어긋나면 정상 요청이 거절되므로 시계 동기화가 전제로 딸려 온다.

## 게이트웨이로 둘 것인가, 옆에 붙일 것인가

인증을 어디서 할지는 배치 문제다. 두 가지가 흔하다.

**게이트웨이 방식**은 모든 트래픽이 앞단을 통과한다. 인증·검사·로깅을 한 곳에서 하니 정책이 새지 않고, 뒤쪽 서비스는 인증을 몰라도 된다. 대신 앞단이 죽으면 전부 멈추고, 지연이 한 번 더 붙는다.

**프록시/사이드카 방식**은 검사기를 호출부 옆에 둔다. 앞단 단일 장애점이 없고 지연이 짧지만, **호출부마다 붙여야 해서** 하나 빠뜨리면 그 경로는 무방비다. 앞서 다른 글에서 적었듯 "기능이 있는 것"과 "그 경로가 실제로 그걸 부르는 것"은 별개다.

둘 다 인증 자체의 강도는 같다. 갈리는 건 **빠뜨릴 수 있느냐**다.

## 넓게 보면

서명과 논스는 각각 **위조**와 **재사용**을 막는다. 이름이 비슷해 하나로 묶기 쉬운데, 하나만 있으면 다른 쪽이 그대로 열린다. 이런 짝은 보안 설계에 자주 나온다 — 무결성과 신선도, 인증과 인가, 암호화와 서명. 각각이 막는 대상을 한 줄로 적어두면 어느 쪽이 비었는지 보인다.

ML 서비스에서도 같은 구분이 필요하다. 모델이 유해 입력을 걸러도 그건 **내용 검사**이지 **호출자 검증**이 아니다. 반대로 인증이 튼튼해도 인증된 사용자가 보내는 공격은 못 막는다. 층마다 무엇을 책임지는지 적어두지 않으면, 어느 층도 안 보는 구멍이 조용히 남는다.

## 메모

- 서명은 내용 변조를 막고, 논스는 재전송을 막는다. 하나만으로는 다른 쪽이 열린다.
- 서명 대상에 메서드·경로·타임스탬프까지 넣는다. 본문만 서명하면 같은 본문을 다른 곳에 보내는 게 통과한다.
- 논스 저장소는 타임스탬프 창으로 유한하게 만든다. 대신 시계 동기화가 전제로 붙는다.
