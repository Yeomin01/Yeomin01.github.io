## 배경

한국어 PII NER 모델(KoELECTRA-base-v3 + CRF, 16 카테고리) 을 학습 중이다. 자체 clean·검수 테스트셋에서 F1 0.98, 자체 hard/OOD 셋에서 F1 0.92 를 내는 상태에서 상담 도메인 실데이터로 회귀 평가를 돌렸다. 결과가 예상 밖이었다.

| 카테고리 | 자체 clean | 자체 hard | 상담 실데이터 |
|---|---|---|---|
| NAME  | 0.99 | 0.97 | **0.56** |
| ADDRESS | 0.97 | 0.98 | **0.26** |
| ACCOUNT | 0.98 | 0.99 | **0.64** |

PHONE·EMAIL 같은 정형 카테고리는 유지되지만 문맥 의존 카테고리 세 개가 절반 이하로 떨어졌다. 카테고리별 support 가 수백~천 단위라 노이즈로 볼 수 없는 수치였다.

## 진단 1 — truncation 은 아니었다

첫 가설은 sample 길이였다. 상담 데이터 sample 은 평균 문자 813, 최대 1,325 로 학습 sample 보다 길었다. tokenizer 로 재보니 최대 674 토큰까지 나왔고 512 초과가 5% 정도, character 위치 기준 512 이상 span 이 26% 였다.

그러나 sample #2 는 tok=339 로 truncation 없이 처리됐는데도 이 sample 의 gold span 여섯 개 중 세 개(NAME 김미영 3회) 를 모두 놓쳤다. Sample 길이는 원인이 아니었다.

## 진단 2 — hybrid 파이프라인 side effect 도 아니었다

두 번째 가설은 BERT 예측 뒤에 붙는 regex overlay 와 postprocess 였다. 이 파이프라인이 BERT span 을 지우는지 확인하려고 짧은 문장 하나를 통째로 넣어봤다.

```
"고객: 성함은 김미영이고, 주소는 서울특별시 강남구 테헤란로 123번지입니다."
```

이 문장에서는 원본 BERT 예측이 `김미영` 을 `B-NAME I-NAME` 으로 정확히 잡았고, hybrid 최종에도 그대로 살아 있었다. 문제는 파이프라인이 아니었다.

## 진단 3 — 긴 상담 컨텍스트에서 BERT 자체가 O 로 확신

같은 김미영이 상담 대화 전체 안에 들어가면 BERT 예측이 완전히 달라졌다. Sample #2 를 통째로 넣고 김미영 위치의 예측 라벨과 confidence 를 뽑았다.

```
첫 등장 (char 322)  → 김미:O(0.96) ##영:O(0.98)
두번째 (char 387)   → 김미:O(1.00) ##영:O(1.00)
세번째 (char 535)   → 김미:O(0.89) ##영:O(0.83)

주소 span "서울특별시 강남구 테헤란로 123번지"
                    → 서울:O(1.00) ##특별:O(1.00) 강남구:O(1.00)
                      테헤란:O(1.00) ##로:O(1.00) 123:O(1.00) ##번:O(1.00) ##지:O(1.00)
```

Confidence 1.00 으로 O 를 확신한다. 학습 분포와 다르다고 판단해 uncertain 하게 예측하는 게 아니라, 완전히 non-PII 라고 확신한다. `010-9876-5432` 는 정확히 잡는다. 형식 있는 정형 PII 는 문제없다.

여러 sample 로 확장해 놓친 값의 top 을 뽑아봤다.

```
NAME 놓친 값 top:
  348x 김민수, 96x 김철수, 93x 홍길동, 37x 김영수, 30x 김영희

ADDRESS 놓친 값 top:
  99x '서울시 강남구 테헤란로 123'
  48x '서울특별시 강남구 테헤란로 123'
  14x '서울시 강남구 역삼동 123-45번지'
```

가장 대표적인 한국 이름과 주소 template 이 그대로 놓친다. 학습 데이터에 포함될 것 같은 이름들이라 학습 세트 라벨링을 확인해봤고, 이 이름들이 학습 문장 안에서 "예시 이름" (마스킹 없이 그대로 노출) 으로 자주 쓰였다는 걸 확인했다.

## 원인

학습 데이터 46만 개는 평서문·문장 단위 합성 위주였다. `고객:` `상담사:` 같은 dialog turn 마커가 학습셋에 아예 없었다. 짧은 단문에 대표 이름이 들어간 라벨링과 자연스러운 예시 문장이 겹치면서, 모델이 "긴 대화체 안의 김민수 = 예시 문장" 이라는 해석을 학습했을 가능성이 크다. 짧은 단문이면 학습 분포에 가까워 잡지만, dialog marker 로 감싸면 컨텍스트 신호가 강해져 non-PII 로 확신하게 된다.

같은 방식으로 ADDRESS, ACCOUNT 도 확인했다. ACCOUNT 는 "은행명 + 계좌번호" 컨텍스트는 잡지만 은행명 없이 숫자만 있으면 못 잡는 경향이 있었다.

## 대응 — augment 를 상담 turn 대화체로 재작성

v7 augment 를 다음 규칙으로 다시 짰다.

- 모든 sample 은 반드시 `상담사:` 와 `고객:` 이 각 최소 1회 등장하는 2~4 턴 대화
- 실제 상담 문맥 (은행, 카드, 쇼핑몰, 통신사, 병원, 공공기관, 보험, 택배 등)
- 카테고리별로 학습 분포에서 약한 부분을 prompt 에 명시:
  - NAME: "김민수·김철수·홍길동 같은 상투적 예시 이름은 피할 것"
  - ACCOUNT: "은행명 없이 숫자만 나오는 케이스도 포함"
  - ADDRESS: 광역시도만·시군구까지만 나오는 문장은 만들지 말 것. 반드시 동 + 지번 / 도로명 + 호수 / 상세 건물명 중 하나 포함. `address` 값은 광역시도부터 상세까지 이어진 전체 span

카테고리 다섯 개 × 5,000 sample. 기존 학습셋 466K 에 25K 를 얹어 v7 학습을 준비 중이다.

Dry-run 결과 5개 중 3~4개가 prompt 를 정확히 따랐다. 광역만 나오는 미준수 케이스가 몇 개 있었고, `max_tokens` 를 900 으로 올려 대화체 응답이 잘리지 않게 조정했다.

```
[address] "고객: 네, 인천광역시 연수구 송도동 12-15, 503호 입니다."
[account] "고객: 신한은행 1234-567-8901 입니다."
[amount]  "고객: 이번 달 사용 요금은 87,500원 입니다."
[rrn]     "고객: 920722-2541893 입니다."
```

## 부수적으로 정리한 것 — 명단 화이트리스트 매칭

같은 벤치마크에서 ORG 도 recall 이 낮게 나왔다. ORG 는 인허가(370만) + DART 비상장(11만) 명단 기반의 화이트리스트로 confirm 하는 구조인데, 완전 일치만 체크하는 로직이라 매칭이 자주 실패하고 있었다. 원인을 뜯어보니 세 가지가 섞여 있었다.

**첫째, 명단에는 있는데 정규화가 못 잡는 경우.** `KB국민은행` 은 명단에 그 문자열로는 없고, `KB국민은행 신관` `(주)KB국민카드` 처럼 지점·부속시설·법인 표기가 붙은 형태로만 존재했다. `IBK기업은행` `배달의민족` 같은 것도 같은 패턴이었다. 해결책으로 로드 시점에 alias 인덱스를 만들었다. 각 명단 항목의 첫 공백/괄호 앞을 잘라 접두 브랜드명을 alias set 에 추가한다. 4자 이상만 유지해 짧은 사람 이름이 alias 로 승격되지 않도록 했다. 인덱스 크기는 raw/normalized 와 겹치는 항목을 뺀 뒤 28만이다.

**둘째, 명단 자체의 노이즈.** 인허가 명단 375만 안에 `김민수` `김철수` `홍길동` 같은 사람 이름과 `서울` `가나` 같은 짧은 대표어가 실제 상호로 등록돼 있었다. BERT 가 이 텍스트를 ORG 로 예측하면 raw 매치로 통과하는 상황이었다. 앞단에 두 개 필터를 붙였다.

```python
_KOREAN_NAME_RX = re.compile(
    r"^[김이박최정조강윤장임한오서신권황안송전홍고문양손배백허유남심노하][가-힣]{2}$"
)
_ORG_HARD_BLACKLIST = frozenset({
    "서울","부산","대구","인천","광주","대전","울산","세종",
    "경기","강원","충북","충남","전북","전남","경북","경남","제주",
    "한국","미국","일본","중국","북한","남한", ...
})
```

그리고 span 길이 2자 이하도 필터에서 걸러냈다. `DB` 는 인허가에 실제 상호로 등록돼 있어서 (`DB` `DB Company` `DB PC방` `DB 손해보험` 등) BERT 가 "DB 서버" 를 ORG 로 오탐하는 경우가 있었다. 실제 2자 브랜드 (KT, LG, SK) 는 인허가 명단에 다른 회사만 있어서 side effect 가 없었다.

**셋째, 정책상 마스킹 대상이 아닌 것들이 통과.** DART 상장사 3,846 개와 글로벌 빅테크 204 개는 public negative 로 마스킹하지 않기로 되어 있는데, 이 reject 가 매칭 로직에 반영돼 있지 않았다. 신한은행·삼성전자·엔비디아·Microsoft 등이 그대로 통과됐다. 두 명단 조회를 함수 앞단에 추가했다.

정리하면 매칭 순서는 이렇게 됐다.

```
A. 길이 2자 이하 → False
B. 사람이름 패턴 → False
C. 지명·국가 blacklist → False
D. DART 상장사 or 글로벌 빅테크 → False
1. raw 완전 일치 → True
2. normalized 일치 → True
3. alias 일치 → True
```

미니 검증 18 케이스 모두 의도대로 나왔다. `KB국민은행` `IBK기업은행` `배달의민족` 이 새로 통과했고, `엔비디아` `Microsoft` `신한은행` 같은 상장사는 모두 reject 됐다.

## 회귀 평가

명단 로직 개선을 뷰어 벤치마크 여덟 개에 적용해 ORG F1 을 재측정했다.

| 셋 | before | after | Δ |
|---|---|---|---|
| clean | 0.411 | 0.591 | **+0.18** |
| inspect | 0.465 | 0.612 | +0.15 |
| ood_det | 0.471 | 0.737 | **+0.27** |
| AIHub OOD | 0.863 | 0.852 | -0.01 |
| KLUE OOD | 0.027 | 0.039 | +0.01 |

Recall 이 15~28%p 오르면서 precision 은 미세하게만 떨어졌다. KLUE 는 라벨 스킴이 우리 정책 (회사·기관·부서) 과 크게 달라 (경찰·검찰·정부·북한·한국 을 ORG 로 라벨) 벤치마크로 부적합하다는 게 다시 확인됐다.

AIHub OOD 는 -1%p 로 미세 회귀했는데, 하드 필터가 유효 케이스를 몇 개 걸러낸 것으로 보인다. 상장사 reject 정책을 강하게 적용한 뒤 다시 측정할 예정이다.

## 남은 것

v7 augment 학습이 뒤에서 돌고 있다. 학습이 끝나면 같은 상담 실데이터에서 NAME·ADDRESS·ACCOUNT recall 이 얼마나 회복되는지 확인할 수 있다. Prompt 조건을 강하게 걸었지만 상담 대화 자체가 학습 데이터에 처음 들어가는 형식이라, 40 만 규모의 평서문 학습셋 위에 25K 대화체 augment 를 얹은 것으로 얼마나 뒤덮을 수 있을지가 관건이다. 결과에 따라 augment 규모나 prompt 를 다시 조정할 것 같다.
