## 서빙 쪽에서 메모리를 재다 찾았다

서빙 쪽에서 컨테이너 메모리(RSS)를 재다가 예상보다 크다는 연락이 왔다. 모델 크기로는 설명되지 않는 1GB가 있었다.

따라가 보니 기관명 명단이었다. 예전에는 텍스트에서 찾은 기관명이 명단에 있는지로 개인정보 여부를 판단했다. 이 방식은 몇 달 전에 폐지됐다. 지금은 기관명이 특정 개인과 묶였는지를 문맥으로 판단하고, 애매한 것은 2차 LLM이 본다. 명단을 확인하는 함수는 남아 있었지만, 지금 파이프라인은 그 함수를 확인 기능을 끈 채(`check_list=False`) 부른다.

## 끈 채로 불러도 명단을 올렸다

함수는 대략 이렇게 생겼다.

```python
def filter_listed_org(spans, check_list=True):
    _preload_org_list()          # 플래그를 보기 전에 먼저 올린다
    if not check_list:
        return spans
    ...
```

플래그를 보기 전에 명단부터 올리고 있었다. 명단은 376만 건이고 메모리로 1GB다. 그래서 쓰지도 않는 명단이 이 함수를 부르는 모든 프로세스에 올라갔다. 프로세스를 시작할 때마다 10~30초가 더 걸리기도 했다.

선로드 코드에는 "인덱스 초기화"라는 주석이 붙어 있었다. 그런데 실제로 명단을 보는 함수는 인덱스를 쓰기 전에 스스로 명단을 불러오고 있었다. 선로드는 처음부터 없어도 되는 코드였다.

## 실측

| 시점 | 프로세스 메모리 |
|---|---|
| import 직후 | 39 MB |
| 고치기 전, 끈 채로 한 번 호출 | 1,117 MB |
| 고친 뒤, 끈 채로 한 번 호출 | 39 MB |

서빙 컨테이너 기준으로는 2,383 MB에서 1,662 MB로 줄었다. 같은 파일을 서빙 쪽도 가져다 쓰고 있어서 양쪽에 똑같이 있던 비용이다.

## 테스트로 고정했다

고친 내용은 단순하다. 플래그를 먼저 보고, 실제로 확인이 필요할 때만 명단을 올린다. 이 동작을 테스트로 고정했다.

- 끈 채로 부르면 명단이 올라가지 않는다(모듈의 명단 객체가 `None`으로 남는다).
- 켜고 부르면 그때 올라간다.
- 켜고 부르더라도 명단을 보기 전에 판단이 끝나는 값(예: 상장 기업처럼 공개 목록으로 먼저 걸러지는 이름)이면 올라가지 않는다.

메모리 같은 비기능 동작은 깨져도 기능 테스트가 통과한다. 그래서 "언제 올라가는가"를 직접 단언하는 테스트가 따로 있어야 다시 생기지 않는다.

## 비용으로 보면

한 프로세스의 1GB는 거기서 끝나지 않는다. 서빙은 워커 수만큼, 레플리카 수만큼 프로세스를 띄운다. 워커 4개짜리 레플리카 3개면 쓰지 않는 명단이 12GB를 차지한다. 컨테이너 메모리 한도를 그만큼 높게 잡아야 하고, 그것이 그대로 인스턴스 크기와 비용이 된다. 시작이 10~30초 느려지면 오토스케일링으로 새 레플리카가 트래픽을 받기까지의 시간도 늘어난다.

## 정리

정책을 바꾸면 옛 정책의 코드는 호출 경로에 남는 경우가 많다. 플래그로 꺼 두면 기능은 멈추지만, 플래그를 보기 전에 하는 일은 계속 비용을 쓴다. 비싼 초기화는 그것이 실제로 필요하다고 판단한 뒤에 한다. 그리고 메모리는 기능 테스트로 드러나지 않으므로, 프로세스 단위로 재고 그 결과를 테스트로 고정한다.
