I grouped by area what I ran into while training, evaluating, and operating a PII detection model (a cascade of NER and second-stage LLM verification) and a multi-turn attack detection model. For each post I wrote down the problem, what I did, the result, and keywords.

## ML — evaluation and data

### [I Was Scoring the Two Stages Against Different Answer Keys](/en/posts/two-stages-two-answer-keys/)

- Problem: Adding second-stage LLM verification after the first-stage NER came out as lowering precision. The second stage only releases what was masked, so that direction is hard to get.
- What I did: I found that each stage was being scored against a different answer key. I rescored with the same answer key and added the ratio of false positives released to true positives lost as a metric. In the same comparison I also found an answer-key defect (1,140 positions where an organization's amount was treated as PII).
- Result: I corrected precision 0.9585 → 0.9631. With the defect accounted for, the release ratio is 0.33:1 → 8.6:1.
- Keywords: cascade evaluation, answer-key consistency, F0.5, gold set versioning

### [The Apparent Improvement Came from Memorizing the Evaluation Set's Templates](/en/posts/eval-set-leaked-without-sharing-a-sentence/)

- Problem: Training data built from looking at evaluation-set false negatives raised the score a lot. The sentence duplication check found zero.
- What I did: I built a placeholder 5-gram template audit and a value-vocabulary audit, and set a criterion for judging the direction of contamination.
- Result: The apparent F1 gain of +0.020 was +0.003 with the contaminated axis removed, and organization-name recall actually dropped. I did not promote that version and quarantined the contaminated data.
- Keywords: data leakage, n-gram audit, evaluation hygiene

### [The Moment You Look into the Gold, It Stops Being Gold for the Next Training Run](/en/posts/looking-at-the-gold-spends-it/)

- Problem: Reinforcing from evaluation-set false negatives contaminates the evaluation set even when no sentence overlaps. Part of the benign data used for threshold calibration (about 14%) was also in the evaluation set.
- What I did: I set four rules covering gap analysis, generation, leakage checks, and dev set wear, and measured again on the data with the overlapping items removed.
- Result: The false positive reduction held out of sample (about 35% → about 34%). I reported the detection cost separately as unverified.
- Keywords: evaluation hygiene, dev set, out-of-sample validation

### [The Gold Set Gets Contaminated Even When Not One Sentence Overlaps](/en/posts/gold-leaks-without-a-shared-sentence/)

- Problem: By user-turn hash, there was almost no overlap between the evaluation set and the training set.
- What I did: I implemented a character 5-gram containment audit as a sparse matrix product. I fixed the parsing omission and the dictionary effect of long documents, and validated the tool by whether it re-caught 100% of the leaks already known.
- Result: About 7% of the training set shared a template with the evaluation set. Zero in the re-audit after removal
- Keywords: containment, sparse matrix, audit tool validation

### [The Retrieval Index Is Also Data the Model Has Seen](/en/posts/the-retrieval-index-was-seen-data/)

- Problem: The kNN index queried at serving time holds only vectors, so it had been left out of the text leakage audit.
- What I did: I embedded the evaluation dialogues with the same encoder as serving and compared by cosine. I set a procedure of first listing "what the model has seen" (training, calibration, index, prompt examples).
- Result: The entire English benign segment of the evaluation set had cosine 1.000 with the index. The same public corpus was the source.
- Keywords: retrieval-based features, embedding audit, data lineage

### [I Could Not Fix the Shipped Model, so I Fixed the Ruler](/en/posts/fix-the-ruler-when-the-model-is-shipped/)

- Problem: Part of the evaluation set overlapped with data the deployed model had seen.
- What I did: Instead of editing the evaluation set, I bumped its version and removed overlapping items by three criteria (exact match, n-gram containment, index proximity). I counted the gaps per cell of language, tone, format, technique, and domain, and set target counts according to what each cell is for.
- Result: About 40% of the existing evaluation items were excluded. I also reran the build and confirmed it gives the same result.
- Keywords: evaluation set versioning, stratified evaluation, labeling principles

### [Retraining with Only More Attacks Came Back as False Positives](/en/posts/retraining-with-attacks-only-returned-false-positives/)

- Problem: Four retraining runs that reinforced weak attack types each multiplied false positives several times over on a different form of benign dialogue.
- What I did: I found the common cause, that the model learns a surface form (language, format, way of speaking) found only in attacks, and settled on the direction of benign controls with the same surface form and paired data. I changed false positive measurement to use per-format benign sets.
- Result: Per-format measurement found a regression that was invisible on the single benign set (false positives on code dialogues 0% → about 19%).
- Keywords: contrastive data, shortcut learning, per-format evaluation

### [State Product Performance as 'How Many Out of 100'](/en/posts/speak-in-weighted-false-positive-rate/)

- Problem: F1 and PR-AUC could not answer "how many of 100 benign requests get blocked".
- What I did: I increased the sample per cell, set traffic weights and per-format ship criteria, and narrowed the recall denominator to match the layer's definition.
- Result: I confirmed that the same model's headline false positive rate moves by more than a factor of two depending on the mix assumption, and switched reporting to the weighted false positive rate and the number of cells that passed.
- Keywords: product metrics, weighted false positive rate, ship criteria

### [What Is Missing from the Answer Key and What Is Wrongly in It Do Not Weigh the Same](/en/posts/missing-and-wrong-labels-weigh-differently/)

- Problem: The answer keys of LLM-generated evaluation documents had a mix of missing labels and over-labeling.
- What I did: I analyzed the scoring code and separated the effects of the two errors. Missing labels narrow the measurement range, and over-labeling creates fake false negatives. I judged a sample by hand to estimate the rate, and designed a binding-judgment step.
- Result: I confirmed that roughly a third of the organization-name answers are over-labeled, and put gap analysis for those labels on hold.
- Keywords: label quality, scoring rule, context-dependent labels

## LLM

### [Give a Small Model All the Conditions at Once and It Drops Them from the Front](/en/posts/small-models-drop-instructions-from-the-front/)

- Problem: Of the evaluation documents made with a 4B model, 29% were usable.
- What I did: I split the task, added an allow list and bad and good examples, and repaired only the format mistakes whose meaning was clear. I corrected duplicated units at the merge step and measured the distribution skew caused by rejection sampling.
- Result: I raised the pass rate 8% → 50% → 71%. I corrected 110 duplicated units without shifting any spans.
- Keywords: prompt design, contrastive examples, rejection sampling bias

### [When a Generative Model Writes Too Few Turns, Force It with a Schema](/en/posts/force-the-shape-with-a-schema/)

- Problem: The 4B model wrote only about 60% of the requested number of turns and wrote the documents short, so only 1 in 8 met the spec.
- What I did: I forced a JSON schema with vLLM structured output (length of the exchange array, minimum length of the document field, an attachment-position field). I handled a parser bug, server errors, blank output, and the token limit.
- Result: First-attempt pass rate 78%; with retries, 963 of 1,000 (96%) were generated in about 23 minutes at concurrency 16.
- Keywords: structured output, JSON schema, synthetic data

### [I Decided to Turn Off the Second-Stage LLM Verification, Then Reversed It the Same Day](/en/posts/turned-off-the-llm-judge-then-back-on/)

- Problem: I decided to turn off second-stage LLM verification based on an evaluation set that covered only one direction.
- What I did: A probe in the opposite direction reversed the decision. I changed the default verdict to "mask", and handled numeric private identifiers with rules. I added a function that returns the grounds for the verdict on each value.
- Result: 0 names wrongly released, over-blocking on 1 of 45 public-figure queries, policy probes 15/15
- Keywords: LLM-as-judge, safe defaults, rule–LLM hybrid, verdict rationale logging

## MLOps

### [I Built a Dev Set for Gap Analysis Without Looking at the Evaluation Set](/en/posts/dev-set-built-without-seeing-the-gold/)

- Problem: Doing gap analysis on the evaluation set contaminates it.
- What I did: I guaranteed the answer key structurally with placeholder-based generation and mixed two LLMs. I set the reinforcement direction from training-set statistics. I built per-ID seeds, resumable writing, re-checks at merge, and a datasheet, and ran the leakage audit in both directions.
- Result: 943 documents, 12,533 answer spans. Rare labels went from 2–16 per label to 170–250.
- Keywords: synthetic data pipeline, reproducibility, data card, leakage audit

### [The Thresholds Were Being Derived on a Copied Path, Not on Serving](/en/posts/threshold-calibrated-on-a-copy/)

- Problem: The copy of inference and post-processing in the threshold derivation script differed from serving in two places (temperature applied to decoding, a post-processing step missing).
- What I did: I deleted the copy and imported the serving functions. I pinned with a test that the same object is used, and derived the thresholds again.
- Result: 41/41 span-level agreement with serving. 1 of 24 values crossed the boundary and was updated per the rule.
- Keywords: training–serving skew, calibration, temperature scaling, CRF

### [I Changed Two Constants Instead of Retraining](/en/posts/two-constants-instead-of-retraining/)

- Problem: While retraining kept failing, a large share of the false positives came from the gate thresholds. The calibration data had no document or code formats.
- What I did: I grid-swept the thresholds on per-format benign data and attacks, counting rescued attacks and new false positives together. I found a dead condition that had never fired, and shipped the constant change as a bundle too.
- Result: Weighted false positive rate down about 35% in the CPU-only configuration (about 13% in the configuration with LLM re-check)
- Keywords: threshold calibration, exchange ratio, dead code, release bundle

### [Load the Model Once and Share It — A Shared vLLM Server](/en/posts/load-the-model-once-share-it-with-vllm/)

- Problem: Two jobs each tried to load the same 4B model. With fixed batching, 500 items were going to take 4 hours.
- What I did: I loaded the model on a single vLLM server and had the jobs share it over HTTP. I separated the serving virtual environment, settled on QAT 4-bit weights and the memory fraction, and added a health check.
- Result: I generated 1,000 multi-turn dialogues in about 23 minutes.
- Keywords: vLLM, continuous batching, PagedAttention, separate serving environment

### [Another vLLM Server Was Already Using the Shared GPU](/en/posts/sharing-a-vllm-server-on-a-shared-gpu/)

- Problem: Another job's vLLM server was using 13.8GB of the shared GPU's 16GB, so I could not load the model.
- What I did: I traced what was holding the memory and, with permission, shared the server running the same model through its OpenAI-compatible API. I adjusted concurrency by watching the load and made the generation job resumable.
- Result: With no additional GPU memory, time per document went from about 5 seconds to about 1.6 seconds.
- Keywords: shared GPU operations, vLLM, concurrency, resumable jobs

### [Rules for Long-Running Jobs on a Shared GPU Server](/en/posts/rules-for-long-jobs-on-a-shared-gpu/)

- Problem: Jobs that run for hours were exposed to dropped sessions, endless restarts, and interfering with other people's jobs.
- What I did: I wrote down the rules: detach from the session with setsid, resume from a state file, give the watchdog a restart cap and stopping as the default, make patches assert the match count, and so on.
- Result: I recorded operating rules that prevent past incidents, such as restarting a normally exited training run dozens of times because the watched path differed from the output path, and the causes of the two small incidents this time.
- Keywords: long-running jobs, watchdog, resume, shared resources

### [Where Were the Checkpoints — The Pointer Was There, the Contents Were Not](/en/posts/where-were-the-checkpoints/)

- Problem: The checkpoints for version comparison existed only on local disk, and the deployed model's DVC pointers had no contents on the remote (a missed push).
- What I did: I confirmed identity against the bundle copy by size and file list. I changed the criterion for a completed registration to "uploaded to the remote and download verified", chose which epochs to keep, and left cards for discarded versions too.
- Result: Keeping only the selected epochs per version instead of 15GB per run, six versions stay under 10GB.
- Keywords: DVC, model registry, checkpoint lineage

### [Swapping Only the Checkpoint Is Not a Release](/en/posts/a-checkpoint-alone-is-not-a-release/)

- Problem: A large part of the improvement lives in the rule code, so replacing only the checkpoint does not reproduce the performance.
- What I did: I defined the release unit as a bundle of weights, calibration, thresholds, rule code, and prompts. I keep a version card, a data summary log, DVC pointers, and a manifest, and preserve the previous edition when replacing an artifact.
- Result: It is managed with 17 DVC pointers, and for the two deployed releases I verified file by file that the contents exist on the remote.
- Keywords: model registry, DVC, reproducibility, release unit

## CI/CD

### [An Equality Test Passes Even When Both Sides Are Cut Together](/en/posts/equality-tests-pass-when-both-sides-are-cut/)

- Problem: A parity test passes a state where the serving and evaluation chains are cut together. In another environment, a real failure occurred with four post-processing stages missing.
- What I did: For each stage I pinned a case where the result must change and a boundary case where it must not. I cut the chain on purpose and confirmed that the tests fail.
- Result: With the deliberately injected fault, 5 tests failed, confirming that they catch the fault.
- Keywords: regression testing, parity testing, fault injection

### [Numbers Were Coming Out with One Rule Silently Turned Off](/en/posts/a-rule-was-silently-off/)

- Problem: Because of a fallback that swallows import failures, the measurement finished without an error even with a rule turned off. Because of an unanchored .gitignore pattern, there was a file that had never been committed.
- What I did: I printed the enabled rules and warnings in the measurement header, and confirmed that the warning actually fires.
- Result: The configuration is logged with every number. I wrote up check items for testing in a fresh clone and for pattern anchors.
- Keywords: silent failure, reproducibility, .gitignore, config provenance logging

## Cloud

### [Choosing an LLM for Data Generation, Access Blocked Me Before the Model Did](/en/posts/llm-backend-access-before-model-choice/)

- Problem: The candidate LLM backends were blocked one after another by an invalid key, unapproved cloud model access, and a lack of credits.
- What I did: I wrote down the order of access checks and made the API and local serving swappable through an OpenAI-compatible interface. Keys were managed only through an environment file.
- Result: The same generation code moved between the API and vLLM, and local throughput was about 3 times that of calling generate directly.
- Keywords: managed LLM services, model access management, secrets management, backend abstraction

### [Every Process Was Loading a 1GB List It Never Used](/en/posts/a-list-loaded-for-nothing/)

- Problem: A function from a retired policy preloaded a 3.76-million-entry list before looking at its flag.
- What I did: I switched to lazy loading and pinned with a test when the list gets loaded.
- Result: Process 1,117MB → 39MB, serving container 2,383MB → 1,662MB
- Keywords: memory optimization, container resources, lazy loading, cost
